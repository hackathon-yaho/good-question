# AI 호출 재시도·시간 예산 v4 요청

- **요청자**: AI 파트
- **작성일**: 2026-08-16
- **우선순위**: 필수
- **대상**: 백엔드 파트

## 배경

통합 테스트에서 간헐적인 `502 MODEL_UPSTREAM_ERROR`가 장면을 조기에 끝내는 일이 있었다.
팀은 비용과 대기 시간이 늘어나는 점을 인지한 뒤, API 크레딧 여유를 전제로 **최초 호출을 포함해
최대 10회, 시도당 최대 10초**를 허용하기로 결정했다. 이 문서는 v3을 대체한다.

AI Worker가 재시도를 단독 소유한다. 백엔드가 같은 요청을 다시 시도하면 호출 수와 지연이 곱해지므로
추가 재시도를 두지 않는다.

## 요구사항

1. 대화 AI Worker의 `/analyze`, `/respond` 정책은 아래와 같다.

   | 항목 | 값 |
   | --- | --- |
   | 시도 횟수 | 최초 요청 포함 최대 10회 |
   | 각 시도 상한 | 최대 10초 |
   | Worker 전체 예산 | 최대 102초 (재시도 간 짧은 backoff 포함) |
   | 재시도 대상 | 408·429·5xx, 네트워크, 모델 JSON/계약 오류, 시도 시간 초과 |
   | 즉시 실패 | 401 인증, 422 요청 계약 오류 |

2. 백엔드의 AI HTTP 연결·읽기 대기값을 기본 설정과 Render 운영 환경 모두
   `AI_SERVER_TIMEOUT_SECONDS=105`로 변경한다. 102초 예산 뒤 응답을 돌려줄 여유를 3초 둔다.
3. 백엔드는 `/analyze`, `/respond`에 별도 재시도를 추가하지 않는다(0회). AI Worker만 재시도한다.
4. 기존 요청·응답 JSON, enum, `X-Internal-Token`, STT/TTS 경로는 변경하지 않는다.
5. 최종 실패 처리도 유지한다. 분석 실패는 빈 분석으로 진행하고, 응답 실패는 검수된
   `character_closing` 안전 폴백으로 끝낸다. 오류 원문이나 아이 발화는 응답·로그에 싣지 않는다.
6. 로그에는 `OPENAI_STATUS_429`, `MODEL_OUTPUT_CONTRACT`, `MODEL_OUTPUT_JSON`,
   `ATTEMPT_TIMEOUT`처럼 안전한 원인 코드와 시각만 남긴다.

## 프론트 영향

한 아이 발화에서 `/analyze`와 `/respond`가 모두 최대 예산을 쓸 수 있어, 최악의 경우 약 204초가
걸릴 수 있다. 프론트가 자체 15초 취소를 걸어서는 안 된다. 별도 프론트 요청서
[message-response-time-budget-v3](../frontend/message-response-time-budget-v3.md)를 따른다.

## 완료 조건

- [ ] 기본 설정과 Render의 `AI_SERVER_TIMEOUT_SECONDS`가 모두 `105`다.
- [ ] 백엔드 AI 클라이언트 재시도는 0회다.
- [ ] Worker 502/504 때 기존 안전 폴백으로 정상 응답한다.
- [ ] `/analyze`·`/respond`의 JSON 스키마와 STT/TTS 기능이 변하지 않는다.
- [ ] 긴 실패 케이스와 정상 케이스를 통합 테스트하고, 안전한 이유 코드만으로 원인을 확인할 수 있다.
