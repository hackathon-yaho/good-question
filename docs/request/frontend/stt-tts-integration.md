# STT / TTS 연동 방식 변경 — 백엔드 처리로 전환

- **요청자**: 백엔드 담당
- **작성일**: 2026-08-12
- **우선순위**: 필수

## 배경

[open-questions Q-16(=B-1)](../../open-questions.md)이 최우선 미결로 올려둔 STT/TTS 방식이
**2안(OpenAI)으로 확정**되었습니다.

| | 1안 Web Speech API | **2안 OpenAI (확정)** |
| --- | --- | --- |
| STT | 브라우저 `SpeechRecognition` | **백엔드** (Whisper) |
| TTS | 브라우저 `SpeechSynthesis` | **백엔드** (OpenAI TTS) |
| iPad | iOS Safari 불안정 | 안정 |

**결정 이유**: MVP 지원 기기 1순위가 iPad인데 1안은 iOS Safari에서 불안정합니다
([PRD 9.3](../../product/prd.md)).

**프론트 작업이 바뀝니다.**

- 브라우저 `SpeechRecognition` · `SpeechSynthesis`를 **사용하지 않습니다**
- 대신 오디오를 녹음해 업로드하고, 음성은 백엔드에서 받아 재생합니다
- [api.md](../../spec/api.md)는 문서 전체가 **1안 기준**으로 쓰여 있어 이 문서와 다릅니다. 이 문서를 따라주세요

## 화면 / 경로

새 화면은 없습니다. 기존 화면의 **연동 방식**만 바뀝니다.

| 화면 | 변경 |
| --- | --- |
| C-3 · C-4 (내 차례) | 마이크 → 브라우저 STT ❌ / **오디오 녹음 후 업로드** ✅ |
| C-5 (보내기) | 요청이 **2단계**로 나뉨 |
| C-3 (캐릭터 대사 재생) | 브라우저 TTS ❌ / **백엔드에서 오디오 받아 재생** ✅ |
| C-6 (응답 대기) | 타임아웃 예산이 구간별로 나뉨 |
| D-5 (재구성 발화) | **키워드 실시간 점등 불가** → 최종 결과 일괄 점등으로 폴백 |
| D-6 · F-1 | 아래 "함께 확인할 것" 참조 |

## 사용자 흐름

**중요: 발화 1회가 요청 3개로 나뉩니다.** 한 요청에 합칠 수 없습니다.

```
1. 캐릭터 대사 재생          ── ③ GET /api/tts 로 받은 오디오
2. 재생 종료 → 마이크 자동 활성화
3. 아이가 말함, 녹음
4. 녹음 종료 → 오디오 업로드  ── ① POST /api/stt          (약 8초)
5. 변환 텍스트 화면 표시 → 아이가 확인·수정                 ← 요청이 갈리는 지점
6. [보내기] 클릭             ── ② POST /messages          (약 10초)
7. 캐릭터 대사 말풍선 즉시 표시
8. 대사 오디오 요청·재생     ── ③ GET /api/tts
9. → 2번으로 반복
```

**5번 때문에 ①과 ②를 합칠 수 없습니다.** [PRD F-05](../../product/prd.md)가
*"변환된 텍스트를 화면에 표시"* 하고 *"보내기 버튼을 눌러 제출"* 하도록 요구하기 때문입니다.
합치면 아이가 확인할 시점이 사라져 요건을 못 맞춥니다.

**7번과 8번을 분리한 이유**: 말풍선을 먼저 띄우고 음성이 따라오게 하면 화면이 멈춰 보이지 않습니다.
응답에 오디오를 같이 실으면 ②의 대기 시간에 TTS 생성 시간이 그대로 더해집니다.

## 요구사항

### 녹음 (① 이전)

- `MediaRecorder`로 오디오를 캡처합니다. 브라우저 기본 포맷 그대로 보내면 됩니다 (Chrome `webm` / iOS Safari `mp4`). 백엔드가 그대로 Whisper에 전달합니다
- **마이크는 캐릭터 발화가 완전히 끝난 뒤** 활성화합니다. 재생 중 활성화하면 캐릭터 음성이 녹음됩니다 ([roles.md 2.3](../../team/roles.md))
- 원본 오디오를 로컬에 저장하지 않습니다

### STT 결과 처리 (① → ②)

- 변환 텍스트를 화면에 표시하고 **아이가 수정할 수 있게** 합니다 (C-5)
- 편집한 경우 ②의 `text`에 편집본, `sttRawText`에 ①이 준 원본을 넣습니다
- **①의 결과가 비면 ②를 호출하지 않습니다.** I-2로 처리하고 다시 말하게 합니다
  → 이것으로 [Q-09(빈 발화)](../../open-questions.md) 문제가 해소됩니다. 서버에 빈 발화를 보내지 마세요

### TTS 재생

- **브라우저 `SpeechSynthesis`를 쓰지 않습니다.** 백엔드가 준 오디오를 재생합니다
- 자동 재생하고, "다시 듣기"는 같은 오디오를 다시 재생하면 됩니다 (재요청 불필요)
- 고정 대사(도입·전개 내레이션, 캐릭터 첫/마지막 대사)는 백엔드가 **미리 만들어 캐시**해두므로 거의 즉시 옵니다. LLM 생성 대사만 생성 시간이 붙습니다

> ⚠️ iOS Safari는 사용자 조작 없이 오디오 자동 재생을 막습니다.
> 첫 화면(도입 진입 등)에서 한 번 사용자 탭을 받아 오디오 컨텍스트를 열어두는 처리가 필요할 수 있습니다.
> **실기 확인이 필요합니다.**

### 아이 이름 치환

**백엔드가 치환해서 내려줍니다.** 프론트는 받은 텍스트를 그대로 표시하세요.

`"ㅇㅇ아, 내 방귀가…"` → `"민준아, 내 방귀가…"` (받침 유무에 따라 `아`/`야` 처리 포함)

TTS도 백엔드가 만들기 때문에 화면 텍스트와 음성이 반드시 일치합니다.

### D-5 키워드 실시간 점등

**불가능합니다.** 2안에는 interim result가 없습니다. 재구성 발화가 끝나고 최종 텍스트가 나온 뒤
**일괄 점등**으로 폴백해주세요.

## 상태별 처리

| 상태 | 화면 처리 |
| --- | --- |
| 녹음 중 | 기존 C-4 |
| **변환 중 (①)** | "변환 중" 표시. 최대 8초 |
| 변환 결과 표시 | C-5. 편집 가능 |
| **응답 대기 (②)** | "응답 대기" 표시. 최대 10초 |
| 음성 로딩 (③) | 말풍선은 이미 떠 있음. 음성만 늦게 도착 |

| 에러 | I-3 |

**AI 서버 장애 시에도 에러가 뜨지 않습니다.** 백엔드가 폴백하도록 만들어 두었습니다
— 분석 실패는 그냥 진행되고, 대사 생성 실패는 고정 마지막 대사로 장면이 넘어갑니다.
아이 화면 관점에서는 이야기가 계속됩니다.

## 연동 API

| 메서드 | 경로 | 용도 | Content-Type |
| --- | --- | --- | --- |
| POST | `/api/stt` | 오디오 → 텍스트 | `multipart/form-data` |
| POST | `/api/sessions/{sessionId}/messages` | 발화 제출 → 캐릭터 응답 | `application/json` |
| GET | `/api/tts?messageId={id}` | 대사 → 오디오 | 응답 `audio/mpeg` |

### `POST /api/stt`

**Request** — `audio` 파트에 녹음 파일

**Response 200**

```json
{ "text": "며느리가 창피해서 계속 참았던 것 같아요." }
```

- 인식 결과가 없으면 `text`는 빈 문자열입니다. 이때 `/messages`를 호출하지 마세요
- **원본 오디오는 저장하지 않습니다.** 메모리에서 처리 후 즉시 폐기합니다 ([PRD 10.3](../../product/prd.md))

### `POST /api/sessions/{sessionId}/messages`

[api.md 3.5](../../spec/api.md)와 **동일합니다.** 오디오가 아니라 텍스트를 보냅니다.

```json
{ "text": "확정 텍스트", "sttRawText": "STT 원본" }
```

응답에 `messageId`가 포함되며, 이 값으로 ③을 호출합니다.

### `GET /api/tts?messageId={id}`

오디오 바이트를 반환합니다. 캐시에 있으면 즉시, 없으면 생성 후 반환합니다.

## 디자인 참고

- 화면 명세 C-3~C-6의 **상태 표시 4종**(녹음 중 / 변환 중 / 응답 대기 / 재생 중)은 그대로 유효합니다. 인터뷰에서 명시된 요구사항입니다
- "변환 중"과 "응답 대기"가 이제 **명확히 다른 구간**이 되었습니다. 각각 최대 8초 / 10초입니다

| **별가루** | 백엔드에서 지급합니다 (이야기 완료 시). 다만 **선택-후순위**라 필수 기능 완료 후 붙습니다 |

### 프론트 구현 상태 (2026-08-12)

`NEXT_PUBLIC_SPEECH_MODE`로 두 경로를 전환합니다.

| 모드 | STT | TTS |
| --- | --- | --- |
| `backend` | `MediaRecorder` → `POST /api/stt` | `GET /api/tts` → `<audio>` |
| `mock` (기본) | 브라우저 `SpeechRecognition` | 브라우저 `SpeechSynthesis` |

| 파일 | 역할 |
| --- | --- |
| `frontend/src/lib/speech/mode.ts` | 모드 전환. 왜 두 경로인지 |
| `frontend/src/lib/speech/backend-stt.ts` | 녹음 → 업로드 → 텍스트 |
| `frontend/src/lib/speech/backend-tts.ts` | 오디오 수신 → 재생 → iOS 잠금 해제 |
| `frontend/src/lib/api/speech.ts` | `POST /api/stt` · `GET /api/tts` |
| `frontend/scripts/verify/speech.mjs` | 백엔드 경로 검증 17건 |

**첫 항목이 아직 안 된 이유**: 백엔드의 `POST /api/stt`·`GET /api/tts`가 아직
없습니다([work-items.md B-13~B-18](../../../backend/docs/work-items.md) 미완).
지금 브라우저 경로를 지우면 **08-20 발표 시연에 음성이 아예 없습니다.** 시연 기기가
노트북 Chrome이라 Web Speech가 동작하고, iPad가 필요한 시점은 주최측 10월 테스트입니다.

두 엔드포인트가 올라오면 `.env.local`에 `NEXT_PUBLIC_SPEECH_MODE=backend`를 넣고,
`browser-stt.ts`·`browser-tts.ts`와 `mode.ts`의 분기를 지우면 이 항목이 충족됩니다.
그때까지도 **백엔드 모드가 실제로 도는지는 검증**하고 있습니다 — `speech` 스위트가
`?speech=backend`로 진짜 녹음·업로드·재생을 태우고, 그 모드에서
**브라우저 음성 API 호출이 0회인지**까지 확인합니다.

**인터페이스는 2안 계약으로 맞췄습니다.** 요청 3분리, "변환 중/응답 대기" 구간 분리,
`messageId` 기반 오디오 요청이 목 모드에서도 그대로 흐릅니다. 백엔드를 붙일 때
처음 실행되는 코드가 생기지 않게 하려는 것입니다.

**백엔드에 확인 요청 3건**을 남겼습니다 →
[request/backend/tts-audio-contract.md](../backend/tts-audio-contract.md)
(`?text=` 경로 · CORS credentials · `messageId` 필드)
