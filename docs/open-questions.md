## 1. 문서 간 충돌

### Q-01 · 인증 방식 — Supabase vs 자체 JWT ✅ 해소

| 문서 | 내용 |
| --- | --- |
| [화면 명세 A-2](spec/screens.md) | "연동: Supabase Auth (OAuth). 성공 시 `parents` 레코드 조회/생성" |
| [PRD 9.1 · I-10](product/prd.md) | "Spring Security + JWT", "Supabase 전제를 적용하지 않음" |
| [작업 분장 3.3](team/roles.md) | "Supabase를 사용하지 않는다" |

**판단**: PRD·작업분장이 2:1이고 더 최신 결정이므로 **자체 JWT가 정답**으로 보입니다.
화면 명세 A-2의 연동 항목이 낡은 것입니다. 확인 후 화면 명세를 고쳐야 합니다.

> ✅ **2026-08-12 결정** — **Spring Security + JWT 확정** ([D-06](../backend/docs/decisions.md)).
> Supabase는 **DB로만** 사용하고 Auth는 쓰지 않습니다.
> **화면 명세 A-2의 "Supabase Auth" 표기 수정이 필요합니다** (프론트 담당).
>
> **추가 결정 (D-18)**: 로그인 자체도 프론트가 카카오 SDK로 code를 받아 백엔드에 보내는
> 방식이 아니라, **백엔드 리다이렉트 방식**(Spring Security `oauth2Login`)입니다. 프론트는
> `GET /api/oauth2/authorization/kakao`로 이동만 하면 되고, 카카오 SDK 연동이 필요 없습니다.
> 로그인 완료 후 `{FRONTEND_URL}/auth/callback?hasCompletedOnboarding=`로 리다이렉트됩니다.
> [api.md 3.1](spec/api.md) 참조.

### Q-03 · B-3 정보 블록의 출처 ✅ 해소

| 문서 | 내용 |

| [PRD F-03](product/prd.md) | 두 문구가 **이야기 단위 고정값으로 확정**되어 있음 |

PRD 확정 문구:

**판단**: `conflict`는 장면별 캐릭터 딜레마([PRD 7.5.1](product/prd.md))이고 이 문구와 성격이 다릅니다.
PRD 값을 쓰는 게 맞고, `stories`에 컬럼 2개를 추가하거나 상수로 두면 됩니다.
주최측이 "이 두 문구는 팀에서 변경 가능"이라고 명시했습니다.

> ✅ **2026-08-12 결정** — **`stories.situation` · `stories.child_role` 컬럼 추가**
> ([D-07](../backend/docs/decisions.md)). 상수 대신 컬럼으로 둔 이유는 `story_id` 분기 코드를 없애기 위함입니다.
> **`conflict`는 화면에 쓰지 않습니다.**

### Q-04 · 미션 표시 형태 — 전체 모달 금지 vs 900px 오버레이 ✅ 해소 (2026-08-12, 프론트 구현)

| 문서 | 내용 |
| --- | --- |
| [PRD 5.2](product/prd.md) (주최측) | "미션을 **별도 화면이나 전체 화면 모달로 구성하지 않는다**" |
| [작업 분장 2.4](team/roles.md) | "전체 화면 모달이나 별도 라우트로 만들지 말고, 대화 영역 안에서 자연스럽게 이어지도록" |
| [화면 명세 C-10 · C-11](spec/screens.md) | "중앙 오버레이 900px / 940px" |

**판단**: 주최측 요건이 명시적이므로 화면 명세를 고쳐야 합니다.
900px 중앙 오버레이는 사실상 전체 화면 모달입니다. 우측 대화 패널(40% ≈ 512px) 안의
인라인 카드로 재설계하거나, 좌측 일러스트 영역을 미션 영역으로 전환하는 방식이 요건에 맞습니다.

✅ **확정 (2026-08-12, 프론트 구현)**: **우측 패널 안의 인라인 카드.** 오버레이를 쓰지
않습니다. 미션 카드가 우측 패널 상단을 최대 50%까지 쓰고, 아래 대화 패널은 그대로
조작 가능합니다. `layout` 검증 스위트가 **미션이 전체 화면 모달이 아닌지**와
미션+C-3·미션+C-4에서 요소가 겹치거나 잘리지 않는지를 확인합니다.

### Q-07 · 음성 재생 기능 vs 원본 미저장 정책 ✅ 해소 (2026-08-12, 프론트 구현)

| [화면 명세 0-3](spec/screens.md) | 같은 정책을 명시. 화면에도 "목소리는 저장되지 않아요" 문구 있음 |

**판단**: 화면 명세가 스스로 이 충돌을 지적하고 있습니다(§7-3 #18).
**기능을 빼거나 TTS로 텍스트를 읽어주는 방식**으로 대체해야 합니다.
후자를 택하면 버튼 문구를 "내 이야기 다시 듣기"로 바꿔야 합니다 — "내 목소리로"는 거짓이 됩니다.

✅ **확정 (2026-08-12, 프론트 구현)**: **후자.** 텍스트를 TTS로 읽어 줍니다.

- D-6 버튼 문구 → **"내 이야기 다시 듣기"**, F-1도 같은 기준
- "내 목소리로"라는 표현을 쓰지 않습니다. `browse` 검증 스위트가 F-1에 그 문구가
  없는지 확인합니다
- 2안(백엔드 TTS)으로 넘어와도 같습니다. 아이 발화 텍스트를 `GET /api/tts?text=`로
  읽습니다 — 원본 오디오는 `POST /api/stt` 직후 참조를 끊어 남는 곳이 없습니다
  (PRD 10.3)

### Q-09 · 빈 발화 "건너뛰기" ✅ 해소

| 문서 | 내용 |
| --- | --- |
| [PRD 8.9](product/prd.md) (주최측) | "STT 변환에 실패해 확정된 텍스트가 없는 경우 **메시지를 생성하지 않는다**" |
| [작업 분장 3.9](team/roles.md) | 같은 내용 |
| [화면 명세 I-2](spec/screens.md) | "건너뛰기" → **빈 발화로 전송** → 서버가 `SHORT`/`UNCLEAR` 판정 → `THINKING` |

**판단**: 빈 발화를 전송하면 규칙 위반입니다. 그런데 아이가 계속 말을 못 할 때
빠져나갈 길이 필요한 것도 사실입니다. 두 가지 대안:

1. **프론트에서만 처리** — 메시지를 만들지 않고 `CHILD_TURN`으로 되돌리며 `consecutive_low_information_turns`만 서버에 알림
2. **캐릭터가 먼저 넘어감** — 서버가 별도 엔드포인트로 "아이가 답하지 못함"을 받아 `GUIDED` 대사를 생성

1안이 스키마 변경 없이 가능합니다. 어느 쪽이든 **`messages`에 빈 `text`를 넣지 않는 것**이 조건입니다.

> ✅ **2026-08-12 자동 해소** — STT를 별도 엔드포인트로 분리하면서
> ([D-02](../backend/docs/decisions.md)) 문제 자체가 없어졌습니다.
>
> ```
> ① POST /api/stt → text가 비면 여기서 끝. 프론트가 I-2 표시
> ② POST /messages → 애초에 호출되지 않음
> ```
>
> `messages`에 빈 `text`가 들어갈 **경로 자체가 존재하지 않습니다.**
> [PRD 8.9](product/prd.md)의 "확정 텍스트가 없으면 메시지를 생성하지 않는다"를 구조적으로 지킵니다.
> **화면 명세 I-2의 "빈 발화로 전송" 서술 수정이 필요합니다** (프론트 담당).

- 외부 크론으로 10분마다 헬스체크 핑 → **슬립 진입 자체를 막음** (가장 효과적)
- 시연 직전 워밍업 요청 (작업분장 권장)
- 첫 요청만 타임아웃 연장 (예: 60초)
- AI 호출 실패 시 백엔드 폴백 — 재시도 1회 후, 최종 실패면 `character_closing` 또는 짧은 중립 반응으로 대체해 **아이 화면이 무한 로딩에 빠지지 않게** 방어

> ✅ **2026-08-12 결정** ([D-02 · D-03](../backend/docs/decisions.md))
>

> ② POST /messages    분석 5초 + 응답 5초 = 10초  ← 15초 이내
> ③ GET  /api/tts     캐시 히트 시 즉시
> ```
>
> **② 타임아웃·재시도 확정**: `/analyze` 5초 · `/respond` 5초 · Whisper 8초, **재시도 전부 0회.**

> **③ 실패 폴백 확정**: `/analyze` 실패 → 빈 분석으로 정상 진행 /

>
> **④ 슬립 방지**: 외부 크론 10분 핑 + 헬스체크에 `SELECT 1`.

>
> ⚠️ **남은 것: 실측.** 배포 후 각 구간을 측정해 프론트에 공유하고, 15초 유지 여부를 그때 정합니다.

**결정: 1안 Web Speech API.** 파이널데이 시연을 **노트북 Chrome**으로 하기로 정해
1안의 유일한 약점(iOS Safari 불안정)이 사라졌습니다. 비용 0에 D-5 키워드 실시간 점등까지 완전 구현됩니다.

> ⚠️ 남는 리스크: [PRD 2.2](product/prd.md)의 **주최측 10월 테스트는 태블릿 대상**입니다.

> 나중에 Whisper로 교체 가능하게 두는 편이 좋습니다. MVP 시연 자체에는 영향 없습니다.

> TTS는 프론트 `SpeechSynthesis`로 직접 재생하므로 O-15(고정 대사 캐싱)와 Render 파일시스템

> ✅ **2026-08-12 결정 — 2안 확정** ([D-01](../backend/docs/decisions.md)).
> **STT·TTS 둘 다 백엔드가 OpenAI API로 처리합니다.** iPad 시연 안정성을 택했습니다.

| --- | --- |
| **필수** | A-2, A-3, A-4, A-5, B-1, B-2, B-3, C-1~C-7, C-12, D-1~D-7 |
| **필수(예외)** | I-1, I-2, I-3, I-4 — 시연 중 사고 방지용. 화면 명세 §6도 7단계에 배치 |

> C-10·C-11(미션)은 [PRD M-50](product/prd.md)에서 **필수**입니다. 다만 Q-04에 따라 형태를 바꿔야 합니다.

목록을 두 곳에서 관리하다 이미 한 번 어긋났으므로, 여기에는 **결정이 필요한 것만** 둡니다.

| 미확보 **문서** (Stitch 프롬프트·대화작동규칙·인터뷰 DOCX·시안) | [reference/README.md](reference/README.md) |

**전부 없이도 개발은 진행 가능합니다.** [assets.md §3](spec/assets.md)에 폴백이 정리되어 있고,
문서 4건은 이미 확보한 자료가 같은 내용을 담고 있습니다.

다만 아래는 결정이 필요합니다.

### Q-19 · 이야기 표지 비율 🟡

[화면 명세](spec/screens.md)에서 표지를 쓰는 화면의 비율이 서로 다릅니다.

| 화면 | 표시 | 비율 |
| --- | --- | --- |
| B-3 대형 표지 | 좌 45% × 전체 높이 = 648×900 | **2:3 세로** |
| B-1 이어하기 히어로 · B-2 카드 그리드 | 카드 내 | **가로** |
| G-1 리포트 목록 | 64px | 정사각에 가까움 |

**판단**: 한 파일을 `object-fit: cover`로 돌려쓰면 세로형에서 좌우가, 가로형에서 위아래가 잘립니다.
가로 4:3 원본 1장 + B-3만 중앙 세로 크롭으로 가는 것을 [assets.md §2-4](spec/assets.md)에 제안했습니다.
주최측에서 어느 비율로 오는지 확인하는 게 먼저입니다.

### Q-20 · 아이 아바타 6종의 제작 주체 🟡

[화면 명세 A-4](spec/screens.md)는 "캐릭터 선택 6종 그리드"를 필수로 두었지만,
**누가 그 6종을 만드는지 어느 문서에도 없습니다.** 주최측 제공 대상인지 팀 제작인지 불명입니다.
DB 컬럼도 없습니다 (Q-11).

**판단**: 주최측 요건(F-01)은 "아이 이름, 나이 등록"만 요구합니다. 아바타는 화면 명세가 추가한 것입니다.
이니셜 + 색상 원형 아바타로 대체하면 에셋 없이 구현되고 요건도 충족합니다 ([assets.md §3-3](spec/assets.md)).
