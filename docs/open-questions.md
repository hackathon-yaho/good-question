## 1. 문서 간 충돌

### Q-01 · 인증 방식 — Supabase vs 자체 JWT 🔴

| 문서 | 내용 |
| --- | --- |
| [화면 명세 A-2](spec/screens.md) | "연동: Supabase Auth (OAuth). 성공 시 `parents` 레코드 조회/생성" |
| [PRD 9.1 · I-10](product/prd.md) | "Spring Security + JWT", "Supabase 전제를 적용하지 않음" |
| [작업 분장 3.3](team/roles.md) | "Supabase를 사용하지 않는다" |

**판단**: PRD·작업분장이 2:1이고 더 최신 결정이므로 **자체 JWT가 정답**으로 보입니다.
화면 명세 A-2의 연동 항목이 낡은 것입니다. 확인 후 화면 명세를 고쳐야 합니다.

### Q-02 · 소셜 로그인 개수 — 카카오만 vs 3종 🟡

| 문서 | 내용 |
| --- | --- |
| [화면 명세 A-2](spec/screens.md) | 카카오·구글·네이버 버튼 3개 |
| [PRD F-01](product/prd.md) | "카카오, 구글, 네이버 중 **1개 이상** 제공" (주최측 요건) |
| [PRD 9.1 · M-01](product/prd.md) | 카카오 로그인 |

**판단**: 요건은 1개 이상이므로 **카카오만으로 충족**됩니다. 화면에 3개를 그려두고 2개가 동작하지 않으면 시연에서 감점 요소가 됩니다. 카카오 1개만 노출하는 쪽이 안전합니다.

✅ **확정 (2026-08-10, 프론트 구현)**: A-2에 카카오 버튼만 렌더합니다. 구글·네이버 버튼은 넣지 않았습니다.

### Q-03 · B-3 정보 블록의 출처 🟡

| 문서 | 내용 |
| --- | --- |

| [PRD F-03](product/prd.md) | 두 문구가 **이야기 단위 고정값으로 확정**되어 있음 |

PRD 확정 문구:

- 이야기 상황: "큰 방귀 때문에 며느리가 집에서 쫓겨날 위기에 놓였어요."

**판단**: `conflict`는 장면별 캐릭터 딜레마([PRD 7.5.1](product/prd.md))이고 이 문구와 성격이 다릅니다.

주최측이 "이 두 문구는 팀에서 변경 가능"이라고 명시했습니다.

### Q-04 · 미션 표시 형태 — 전체 모달 금지 vs 900px 오버레이 🔴

| [작업 분장 2.4](team/roles.md) | "전체 화면 모달이나 별도 라우트로 만들지 말고, 대화 영역 안에서 자연스럽게 이어지도록" |

### Q-09 · 빈 발화 "건너뛰기" 🔴

| 문서 | 내용 |
| --- | --- |
| [PRD 8.9](product/prd.md) (주최측) | "STT 변환에 실패해 확정된 텍스트가 없는 경우 **메시지를 생성하지 않는다**" |
| [작업 분장 3.9](team/roles.md) | 같은 내용 |

1안이 스키마 변경 없이 가능합니다. 어느 쪽이든 **`messages`에 빈 `text`를 넣지 않는 것**이 조건입니다.

### Q-14 · 응답 시간 예산이 맞지 않음 🔴

| 문서 | 내용 |
| --- | --- |
| [화면 명세 C-6](spec/screens.md) | 15초 초과 → I-3 네트워크 오류 |
| [작업 분장 5장](team/roles.md) | "한 턴에 AI 호출이 두 번 발생한다. **각 5초씩만 잡아도 10초**이며, 여기에 STT와 콜드 스타트가 더해진다" |
| [작업 분장 3.11](team/roles.md) | Render 무료 티어, 15분 무활동 시 슬립, 콜드 스타트 **수십 초**. AI 서버도 무료 티어면 홉이 두 개 |

```
AI 분석 5초 + AI 응답 5초 = 10초
  + STT (2안이면 오디오 업로드 왕복)
  + Render 콜드 스타트 (수십 초)
────────────────────────────────
프론트 타임아웃 예산 15초  ← 초과
```

**판단**: 정상 동작에서도 10초를 쓰므로 여유가 5초뿐이고, 콜드 스타트가 끼면 확실히 터집니다.
[작업 분장 5장](team/roles.md)이 "타임아웃과 실패 처리를 **반드시** 정한다"고 명시한 이유입니다.
네 가지를 병행하는 게 안전합니다.

- 외부 크론으로 10분마다 헬스체크 핑 → **슬립 진입 자체를 막음** (가장 효과적)
- 시연 직전 워밍업 요청 (작업분장 권장)
- 첫 요청만 타임아웃 연장 (예: 60초)
- AI 호출 실패 시 백엔드 폴백 — 재시도 1회 후, 최종 실패면 `character_closing` 또는 짧은 중립 반응으로 대체해 **아이 화면이 무한 로딩에 빠지지 않게** 방어

> 백엔드→AI 타임아웃·재시도 횟수·최종 실패 응답은 [작업 분장 5장](team/roles.md)이
> "정해야 할 것"으로 남긴 미결 항목입니다. B-4로 올렸습니다.

### Q-18 · soft-cue와 `/respond` 입력 🟢

[PRD 6.14](product/prd.md)는 `NORMAL` soft-cue의 재료를 `softRemainingWorry`라는 별도 값으로 정의하지만,
[작업 분장 4.2](team/roles.md)의 입력 스키마에는 `remainingWorry` 하나뿐이고
responseMode 표의 `NORMAL` 항목은 유도 재료 사용을 언급하지 않습니다.

**판단**: soft-cue는 선택 작업(O-13)이라 급하지 않고, 새 필드도 필요 없습니다.
구현할 때 `responseMode = NORMAL`에 `remainingWorry`를 실어 보내고,
프롬프트에서 "NORMAL + remainingWorry면 **약하게만** 드러낸다"를 명시하면 됩니다.
미구현이면 `NORMAL` 일반 반응으로 동작하므로 문제없습니다.

### Q-21 · A-4 진입 경로에 동의 화면이 없다 ✅ 해결 (2026-08-10)

| 문서 | 내용 |
| --- | --- |
| [화면 명세 A-4](spec/screens.md) | 진입 = "A-3, **A-5의 '+ 아이 추가'**, H-2의 '+ 아이 추가하기'" |
| [api.md 3.2](spec/api.md) | `POST /api/children`은 `consents`를 **필수로** 받는다 |
| DB | `child_consents`는 `child_id` FK — **아이 한 명당 한 건** |

A-5에서 둘째 아이를 추가하면 A-4로 곧장 가는데, 그 경로에는 동의를 받는 화면이 없습니다.
동의 값 없이 `POST /api/children`을 부를 수 없고, 프론트가 임의로 `true`를 채우면 요건 위반입니다.

**해결**: A-5 "+ 아이 추가"와 아이 0명 자동 이동을 **A-3(`/onboarding/consent`)으로** 보냅니다.
A-3 → A-4 순서는 그대로입니다. A-4에는 동의 값이 없을 때 A-3으로 되돌리는 안전망을 뒀습니다.

### Q-22 · A-4 "나중에 추가하기" vs A-5 "0명이면 A-4로" ✅ 해결 (2026-08-10)

두 체크리스트가 서로를 무효화합니다. A-4에서 건너뛰면 아이가 0명인 채로 A-5에 도착하고,
A-5는 아이가 0명이면 다시 A-4로 보냅니다. 무한 왕복입니다.

**해결**: **아이가 이미 있을 때만** A-4에 "취소"를 노출합니다. 온보딩 첫 등록에는 건너뛰기가 없습니다.
아이 0명으로는 서비스에서 할 수 있는 일이 없으므로 빠져나갈 길을 만들 이유도 없습니다.

### Q-12 · 별가루(포인트) 시스템 🟢

**판단**: **MVP에서 빼는 것을 권장합니다.** 주최측 요건에 없고, 보상 구조는
[인터뷰 원문](reference/interview-findings.md)에서도 "범위 밖"으로 분류됐습니다.
칩 자리를 비우기 싫다면 "완료한 이야기 N편" 같은 기존 통계로 대체하세요.

✅ **확정 (2026-08-10, 프론트 구현)**: B-1에 별가루 칩을 넣지 않았습니다. 화면에만 있는 숫자는 근거가 없습니다.

## 3. 정책이 안 정해진 것

### Q-13 · 마이크 자동 시작 여부 🟡

[화면 명세 C-4](spec/screens.md)가 결정을 남겨둔 항목입니다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 자동 시작 | 아이 조작 최소화 | 준비 안 됐을 때 잡음 유입 |
| 탭 시작 | 명확함 | 아이가 버튼을 눌러야 함 |

**판단**: 화면 명세의 결론(**자동 시작 + 재시작 버튼 제공**)이 인터뷰의 "조작 최소화" 요구에 맞습니다.
단, [작업 분장 2.3](team/roles.md)의 "캐릭터 발화가 끝난 뒤 활성화" 규칙을 반드시 지켜야 합니다 —
발화 중 활성화하면 캐릭터 음성이 녹음됩니다.

### Q-15 · 카드 순서 재시도 횟수 제한 🟢

`attempt_count` 컬럼이 있다는 점에서 재시도가 전제되지만, 제한 규칙은 어디에도 없습니다.

**판단**: 3회 실패 시 정답 순서를 보여주고 넘기는 쪽을 권장합니다.
무한 재시도는 아이가 갇히고, [D-3](spec/screens.md)의 "실패를 지적하지 않는다" 원칙과도 충돌합니다.

### Q-16 · STT/TTS 방식 ✅ 해결 (2026-08-10)

| | 1안 Web Speech API | 2안 Whisper + OpenAI TTS |
| --- | --- | --- |
| 비용 | 무료 | 소액 유료 |
| iPad (지원 기기 1순위) | ⚠️ iOS Safari 불안정 | ✅ 안정 |
| D-5 키워드 실시간 점등 | ✅ 가능 | ❌ 폴백 필요 |
| 백엔드 작업 | 없음 (텍스트만 수신) | 오디오 업로드 엔드포인트 추가 |

**결정: 1안 Web Speech API.** 파이널데이 시연을 **노트북 Chrome**으로 하기로 정해
1안의 유일한 약점(iOS Safari 불안정)이 사라졌습니다. 비용 0에 D-5 키워드 실시간 점등까지 완전 구현됩니다.

> ⚠️ 남는 리스크: [PRD 2.2](product/prd.md)의 **주최측 10월 테스트는 태블릿 대상**입니다.
> 그때는 iOS Safari에서 Web Speech API가 문제가 될 수 있으므로, STT 호출부를 인터페이스로 분리해
> 나중에 Whisper로 교체 가능하게 두는 편이 좋습니다. MVP 시연 자체에는 영향 없습니다.
>
> TTS는 프론트 `SpeechSynthesis`로 직접 재생하므로 O-15(고정 대사 캐싱)와 Render 파일시스템
> 초기화 문제는 해당 없습니다.

### Q-19 · 이야기 표지 비율 🟡

[화면 명세](spec/screens.md)에서 표지를 쓰는 화면의 비율이 서로 다릅니다.

| 화면 | 표시 | 비율 |
| --- | --- | --- |
| B-3 대형 표지 | 좌 45% × 전체 높이 = 648×900 | **2:3 세로** |
| B-1 이어하기 히어로 · B-2 카드 그리드 | 카드 내 | **가로** |
| G-1 리포트 목록 | 64px | 정사각에 가까움 |

**판단**: 한 파일을 `object-fit: cover`로 돌려쓰면 세로형에서 좌우가, 가로형에서 위아래가 잘립니다.
가로 4:3 원본 1장 + B-3만 중앙 세로 크롭으로 가는 것을 [assets.md §2-4](spec/assets.md)에 제안했습니다.
주최측에서 어느 비율로 오는지 확인하는 게 먼저입니다.

### Q-20 · 아이 아바타 6종의 제작 주체 🟡

[화면 명세 A-4](spec/screens.md)는 "캐릭터 선택 6종 그리드"를 필수로 두었지만,
**누가 그 6종을 만드는지 어느 문서에도 없습니다.** 주최측 제공 대상인지 팀 제작인지 불명입니다.
DB 컬럼도 없습니다 (Q-11).

**판단**: 주최측 요건(F-01)은 "아이 이름, 나이 등록"만 요구합니다. 아바타는 화면 명세가 추가한 것입니다.
이니셜 + 색상 원형 아바타로 대체하면 에셋 없이 구현되고 요건도 충족합니다 ([assets.md §3-3](spec/assets.md)).
