## 수정 이력

### 2026-08-15 — 반복 저정보 발화가 장면을 강제 종료하는 문제

`싫어`·`닥쳐`처럼 장면 내용이 없는 말을 반복했을 때, 현재 백엔드가 모든 메시지를 진행 턴으로
세고 `maxTurns`를 먼저 적용해 다음 장면으로 넘기는 것이 확인됐다. 이는 GUIDED가 아이를 다시
생각하게 돕는 역할과 맞지 않는다.

- AI 서버: 명백한 한마디 거절·회피·공격을 `SHORT_RESPONSE`·`SHORT`·빈 요소로 고정한다.
- 백엔드: 저정보 발화가 진행·미션 턴과 자동 종료를 소모하지 않도록
  [구현 요청](request/backend/low-engagement-turn-protection.md)을 전달했다.
- 프론트: 기존 "이야기 나가기"를 유지한다. 저정보 반복만으로 자동 다음 장면 이동하지 않는다.

백엔드 구현·통합 테스트 전까지는 **미해결** 상태다.

### 2026-08-15 — AI 재시도·시간 예산 재확정

실제 모델 응답 실패가 즉시 502로 끝나는 것을 확인해, 팀 합의로 기존 D-03의 **5초·재시도 0회**를
대체했다. 새 정본은 [API 명세 2.5](spec/api.md)와
[AI 호출 재시도·시간 예산 v2 요청](request/backend/ai-retry-deadline-v2.md)이다.

| 항목 | 현재 결정 |
| --- | --- |
| AI 서버 `/analyze`, `/respond` | 요청 전체 10초, 최초 요청 포함 최대 3회 |
| 재시도 소유자 | AI 서버만. OpenAI SDK와 백엔드는 0회 |
| 백엔드 연결 대기 | 10초 (`AI_SERVER_TIMEOUT_SECONDS`, D-51) |
| 최종 오류 | 시간 초과는 504, 모델/구조화 출력 실패는 502 |
| 백엔드 폴백 | 분석 실패는 빈 분석, 응답 실패는 `character_closing`; 프론트 500 금지 |

한 `POST /messages`가 AI 두 호출을 모두 수행하면 최악 20초가 될 수 있어, 기존의 프론트 15초
보장은 철회한다. 프론트 중단 로직과 실측은
[별도 검증 요청](request/frontend/message-response-time-budget-v2.md)으로 남겼다.

### Q-04 · 미션 표시 형태 — 전체 모달 금지 vs 900px 오버레이 ✅ 해소 (2026-08-12, 프론트 구현)

| 문서 | 내용 |
| --- | --- |
| [PRD 5.2](product/prd.md) (주최측) | "미션을 **별도 화면이나 전체 화면 모달로 구성하지 않는다**" |
| [작업 분장 2.4](team/roles.md) | "전체 화면 모달이나 별도 라우트로 만들지 말고, 대화 영역 안에서 자연스럽게 이어지도록" |
| [화면 명세 C-10 · C-11](spec/screens.md) | "중앙 오버레이 900px / 940px" |

**판단**: 주최측 요건이 명시적이므로 화면 명세를 고쳐야 합니다.
900px 중앙 오버레이는 사실상 전체 화면 모달입니다. 우측 대화 패널(40% ≈ 512px) 안의
인라인 카드로 재설계하거나, 좌측 일러스트 영역을 미션 영역으로 전환하는 방식이 요건에 맞습니다.

✅ **확정 (2026-08-12, 프론트 구현)**: **우측 패널 안의 인라인 카드.** 오버레이를 쓰지
않습니다. 미션 카드가 우측 패널 상단을 최대 50%까지 쓰고, 아래 대화 패널은 그대로
조작 가능합니다. `layout` 검증 스위트가 **미션이 전체 화면 모달이 아닌지**와
미션+C-3·미션+C-4에서 요소가 겹치거나 잘리지 않는지를 확인합니다.

✅ **한 항목씩 순차 진행으로 개편 (2026-08-13 2차)**

4항목을 한 번에 다 말하게 하지 않습니다. 카드가 [브리프 → 발화 → 브리프]로
**네 번 돌아옵니다.**

| 단계 | 우측 패널 |
| --- | --- |
| 브리프 | 미션 카드 (세로 중앙) + 카드 밖 `말해볼래요`. **마이크를 그리지 않는다** |
| 발화 | 카드를 감추고 마이크. 지금 말할 항목만 한 줄로 남긴다 |

- **TTS가 끝나도 자동으로 아이 차례가 되지 않습니다.** 아이가 미션을 읽고 생각한 뒤
  `말해볼래요`로 시작합니다. 예전에는 카드와 마이크가 동시에 떠서, 읽는 중에 이미
  말할 차례였습니다
- 체크리스트를 **1열 4행**으로 바꿨습니다. 읽는 순서가 곧 말하는 순서가 됩니다.
  2×2를 택한 근거("세로 1열은 4개 중 2개만 보인다")는 브리프에서 마이크를 빼면서
  사라졌습니다
- 오버레이가 아니라는 원칙은 그대로입니다. 여전히 우측 패널 안의 인라인 카드입니다
- 순차 진행의 게이트는 **백엔드 신호가 필요합니다** — 미션 1의 1·2번이 둘 다
  `SOLUTION`이라 `accumulatedElements`로 구분할 수 없습니다
  ([요청 문서](request/backend/mission-progress.md)). 지금은 미션 안에서의 발화 횟수로
  넘기고, 완료 표시의 뜻은 **"말했어요"** 입니다
- `mission` 검증 스위트가 이 흐름 전체를 확인합니다 (브리프 → 말해볼래요 → 발화 →
  브리프 복귀 · 1열 · 현재 항목 하이라이트 · 완료 표시)

### Q-18 · soft-cue와 `/respond` 입력 ✅ 구현 완료 (2026-08-12)

[PRD 6.14](product/prd.md)는 `NORMAL` soft-cue의 재료를 `softRemainingWorry`라는 별도 값으로 정의하지만,
[작업 분장 4.2](team/roles.md)의 입력 스키마에는 `remainingWorry` 하나뿐이고
responseMode 표의 `NORMAL` 항목은 유도 재료 사용을 언급하지 않습니다.

**판단**: soft-cue는 선택 작업(O-13)이라 급하지 않고, 새 필드도 필요 없습니다.
구현할 때 `responseMode = NORMAL`에 `remainingWorry`를 실어 보내고,
프롬프트에서 "NORMAL + remainingWorry면 **약하게만** 드러낸다"를 명시하면 됩니다.
미구현이면 `NORMAL` 일반 반응으로 동작하므로 문제없습니다.

**구현 완료** ([backend/docs/decisions.md D-23](../backend/docs/decisions.md)): 백엔드가 판단한
대로 새 필드 없이 `GuidanceSelector.selectForTurn()`이 GUIDED와 같은
`guidanceTarget`/`remainingWorry`를 `responseMode: NORMAL`에도 함께 실어 보낸다. AI 프롬프트
쪽에 "NORMAL + remainingWorry면 약하게만" 지시를 넣는 건 AI 담당 몫으로 남아 있다 — 백엔드는
mock 스텁 기준으로 필드 전달까지만 검증했다.

### Q-22 · A-4 "나중에 추가하기" vs A-5 "0명이면 A-4로" ✅ 해결 (2026-08-10)

### Q-15 · 카드 순서 재시도 횟수 제한 ✅ 해소

`attempt_count` 컬럼이 있다는 점에서 재시도가 전제되지만, 제한 규칙은 어디에도 없습니다.

**판단**: 3회 실패 시 정답 순서를 보여주고 넘기는 쪽을 권장합니다.
무한 재시도는 아이가 갇히고, [D-3](spec/screens.md)의 "실패를 지적하지 않는다" 원칙과도 충돌합니다.

> ✅ **2026-08-12 결정** — **3회 제한** ([D-10](../backend/docs/decisions.md)).
> 3회째 응답에 `correctOrder`와 `retellingKeywords`가 함께 실립니다.
> 통과시켜도 `is_order_correct = false`로 저장하되, **아이 화면에는 실패를 표시하지 않습니다.**

✅ **프론트 구현 완료 (2026-08-12)**

- **횟수를 프론트가 세지 않습니다.** 응답의 `correctOrder`가 실려 왔는지만 봅니다.
  프론트가 세면 서버가 한도를 바꿀 때 두 곳이 어긋납니다 (§0-2)
- 3회째에는 **D-3(오답 피드백)으로 보내지 않습니다.** 거기에는 "다시 해보기"가
  있는데 다음 시도가 없습니다. 정답 순서를 보여주고 곧바로 D-4로 넘깁니다
- **D-4를 재사용합니다.** 화면을 따로 만들면 그 자체가 "너는 다른 길로 왔다"는
  표시가 됩니다. 배너 문구와 카드 색만 바뀝니다 — "순서를 맞췄어!" → **"이런 순서였어!"**
- 맞혔다고 하지도 않습니다. 거짓이고 아이도 압니다
- `activity` 검증 스위트가 1·2회째에 정답이 새지 않는지, 3회째에 재시도 버튼이
  사라지고 "틀렸/실패/오답/정답은/점수" 표현이 없는지, 다음 단계로 나갈 길이
  있는지를 확인합니다

> ⚠️ **2026-08-13 · 화면 명세에서 의도적으로 벗어난 부분** — [D-3](spec/screens.md)은
> 오답 피드백에 **빨간색을 쓰지 말라**고 했지만, 1·2회째 "확인하기" 뒤에 카드 테두리를
> 빨갛게 표시했습니다. **사용자(프론트 담당) 요청**이고, 아이가 "무엇을 다시 봐야
> 하는지" 알 수 있는 신호가 색뿐이었기 때문입니다.
>
> 대신 원칙이 지키려던 것은 남겼습니다 — **"틀렸어요"라고 말하지 않고**, 점수·개수를
> 세지 않으며, **3회째에는 빨간 테두리를 붙이지 않습니다** (다음 시도가 없는데
> 지적만 남기는 게 되므로). 테두리는 "다시 볼 곳" 표시이고 판정 문구가 아닙니다.

✅ **칸 단위로 좁혔습니다 (2026-08-13 2차)**

- 배치 전체가 아니라 **틀린 칸만** 표시합니다. `slotResults: boolean[]`가 응답에
  실려 있을 때만이고, 없으면 예전처럼 전체를 표시합니다
  ([요청 문서](request/backend/order-slot-results.md))
- **맞은 칸에 초록 테두리를 넣지 않습니다.** 넣으면 정답 개수를 세는 화면이 됩니다
- 정답 순서 자체는 여전히 내려받지 않으므로 프론트가 정답을 역산하지 못합니다

> 🐛 **구현 중에 찾은 결함** — 1차의 빨간 테두리는 **실제로 그려지지 않고 있었습니다.**
> `border-secondary`를 먼저 붙이고 뒤에 `border-danger`를 덧붙였는데, 두 유틸리티는
> 우선순위가 같아 클래스 문자열 순서로는 이기지 못합니다(스타일시트 순서가 이깁니다).

> 테두리·배경을 **하나만 고르도록** 고치고, 계산된 색을 확인하는 검사를 넣었습니다.

## 5. 미확보 자료

목록을 두 곳에서 관리하다 이미 한 번 어긋났으므로, 여기에는 **결정이 필요한 것만** 둡니다.

| 미확보 **에셋** (일러스트·로고·아바타·약관·효과음) | [spec/assets.md](spec/assets.md) — 규격·수령 상태·대체 계획 |
| 미확보 **문서** (Stitch 프롬프트·대화작동규칙·인터뷰 DOCX·시안) | [reference/README.md](reference/README.md) |

**전부 없이도 개발은 진행 가능합니다.** [assets.md §3](spec/assets.md)에 폴백이 정리되어 있고,
문서 4건은 이미 확보한 자료가 같은 내용을 담고 있습니다.

다만 아래는 결정이 필요합니다.

### Q-19 · 이야기 표지 비율 🟡

[화면 명세](spec/screens.md)에서 표지를 쓰는 화면의 비율이 서로 다릅니다.

| 화면 | 표시 | 비율 |
| --- | --- | --- |
| B-3 대형 표지 | 좌 45% × 전체 높이 = 648×900 | **2:3 세로** |
| B-1 이어하기 히어로 · B-2 카드 그리드 | 카드 내 | **가로** |
| G-1 리포트 목록 | 64px | 정사각에 가까움 |

**판단**: 한 파일을 `object-fit: cover`로 돌려쓰면 세로형에서 좌우가, 가로형에서 위아래가 잘립니다.
가로 4:3 원본 1장 + B-3만 중앙 세로 크롭으로 가는 것을 [assets.md §2-4](spec/assets.md)에 제안했습니다.
주최측에서 어느 비율로 오는지 확인하는 게 먼저입니다.

> 🟡 **2026-08-13 현재 미해소.** 표지는 여전히 미수령입니다.
> **프론트는 이 결정을 기다리지 않습니다** — 세 화면 모두 규격에 맞는 플레이스홀더가
> 들어가 있고 `coverImageUrl`만 채우면 교체됩니다. 비율이 어느 쪽으로 오든
> `object-fit: cover`로 잘리는 방향만 달라지고 레이아웃은 흔들리지 않습니다.
> 즉 **차단 항목이 아니라 화질 항목**입니다.

### Q-20 · 아이 아바타 6종의 제작 주체 ✅ 해소

[화면 명세 A-4](spec/screens.md)는 "캐릭터 선택 6종 그리드"를 필수로 두었지만,
**누가 그 6종을 만드는지 어느 문서에도 없습니다.** 주최측 제공 대상인지 팀 제작인지 불명입니다.
DB 컬럼도 없습니다 (Q-11).

**판단**: 주최측 요건(F-01)은 "아이 이름, 나이 등록"만 요구합니다. 아바타는 화면 명세가 추가한 것입니다.
이니셜 + 색상 원형 아바타로 대체하면 에셋 없이 구현되고 요건도 충족합니다 ([assets.md §3-3](spec/assets.md)).

> ✅ **2026-08-13 해소** — **팀이 직접 제작해 6종을 수령했습니다**
> (병아리·여우·곰·토끼·거북이·고양이. [assets.md §1](spec/assets.md)).
> 주최측 제공 대상이 아니었습니다.

✅ **프론트 구현 완료 (2026-08-13)**

- **`avatar_id` 값은 `color1`~`color6`을 그대로 씁니다.** 동물 이름(`fox` 등)으로 바꾸지
  않았습니다 — 이미 저장된 값이 있고, 백엔드가 값을 검증하지 않기로 한([D-08](../backend/docs/decisions.md))
  이유가 "프론트가 값을 바꿀 때마다 백엔드를 고치게 된다"는 것이었습니다. 매핑만 바꿨습니다
- 이미지 로드가 실패하면 **이니셜+색상 폴백으로 자동 전환**합니다. 폴백을 지우지
  않았습니다 — 파일 하나가 깨져도 아이 화면에 빈 칸이 생기지 않습니다
- 선택 화면(A-4·A-5·F-1)의 접근성 이름은 색상 키가 아니라 **동물 이름**입니다
  (`캐릭터 곰`). 아이·보호자에게 `color3`은 아무 뜻이 없습니다
- 배경이 종이 질감이라 **알파 채널을 파지 않고 CSS 원형 마스크로** 잘라 씁니다
