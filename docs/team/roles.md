# 굿퀘스천 MVP — 파트별 작업 분장

| 항목 | 내용 |
| --- | --- |
| 문서명 | 굿퀘스천 MVP 파트별 작업 분장 |
| 팀명 | 해커톤오이쉬 |
| 기준 문서 | [../product/prd.md](../product/prd.md) |
| 작성일 | 2026-08-06 |
| 버전 | v1.0 |

이 문서는 PRD의 77개 구현 항목을 담당자 기준으로 재편성한 것이다. 각 담당자는 자기 섹션만 읽어도 작업 범위를 파악할 수 있다. 항목별 상세 정의와 근거는 PRD를 참조한다.

---

## 0. 시스템 구조와 역할 경계

```
프론트엔드  ──HTTP──▶  백엔드  ──HTTP──▶  AI 서버  ──▶  OpenAI
   (Vercel)              │                (gpt-5-mini)
                         │
                         └── PostgreSQL
                             (상태·기록 전부 여기)
```

역할 원칙:

| 주체 | 책임 |
| --- | --- |
| 프론트엔드 | 화면, 음성 입출력, 사용자 상호작용 |
| 백엔드 | 오케스트레이션, 상태 관리, 규칙 판단, 데이터 저장 |
| AI 서버 | 발화 분석, 캐릭터 대사 생성. **상태 없음, DB 접근 없음** |

AI 서버는 상태를 갖지 않는다. 백엔드가 매 호출마다 필요한 값을 전부 실어 보내고, AI 서버는 받은 것만 보고 응답한다. 이 구조를 택한 이유는 두 가지다.

- AI 담당자가 DB 스키마를 몰라도 독립적으로 작업할 수 있다
- AI 서버를 재시작하거나 재배포해도 진행 중인 세션이 깨지지 않는다

## 1. 착수 전 3인 합의 사항

작업 시작 전에 반드시 함께 결정해야 하는 항목이다. 이것이 정해지지 않으면 각자 다른 것을 만들게 된다.

| 결정 항목 | 왜 먼저인가 | 영향받는 담당 |
| --- | --- | --- |
| STT 방식 (Web Speech API vs Whisper) | 백엔드가 텍스트만 받을지, 오디오 업로드 API를 만들지가 갈린다 | 프론트·백엔드 |
| TTS 방식 | 프론트에서 재생할지, 백엔드가 음성 파일을 내려줄지가 갈린다 | 프론트·백엔드 |
| API 응답 스키마 | 확정 전에는 프론트가 화면을 그릴 수 없다 | 프론트·백엔드 |
| 백엔드↔AI 계약 | 8장 참조 | 백엔드·AI |

> **STT 방식이 가장 급하다.** Web Speech API를 선택하면 백엔드는 텍스트만 수신하고,
> OpenAI Whisper를 선택하면 오디오 업로드 엔드포인트가 추가로 필요하다.
> 프론트와 백엔드 양쪽의 작업 범위가 달라진다.

관련: [PRD 9.3](../product/prd.md) STT/TTS 권장안, [../spec/api.md](../spec/api.md) API 계약 초안

## 2. 프론트엔드 담당

### 2.1 필수 — 화면 구현

화면 11개다. 아래 표에서 "홈 내"로 표기된 항목은 독립 화면이 아니라 홈 화면 내부 영역이다.

#### 계정·진입 영역

| 화면 | 구성 요소 |
| --- | --- |
| 로그인 | 카카오 로그인 버튼 |
| 회원가입 | 보호자 계정 생성 |
| 아이 프로필 등록 | 이름, 출생연도 입력. 계정당 최대 3명 |
| 아동 개인정보 처리 동의 | 동의 없으면 이야기 진행 불가 |
| 아이 선택 | 로그인 후 진입. 등록된 아이 중 선택 |

#### 홈·탐색 영역

| 화면 | 구성 요소 |
| --- | --- |
| 홈 | 홈 / 이야기 / 단어장 / 마이페이지 탭 4개. 단어장은 선택 기능이나 **탭 자리는 필수** |
| 홈 내 진행 중 이야기 | 카드 + 이어하기 버튼 |
| 홈 내 추천 이야기 | 2~3개. 추천 로직 없음. 서버가 주는 목록을 그대로 표시 |
| 이야기 목록 | 대표 이미지, 제목, 예상 시간, 주요 주제 |
| 주제별 필터 | `stories.topics` 기준 |
| 이야기 상세 | 이야기 도입 / 이야기 상황 / 아이 역할 3개 블록 |

#### 이야기 진행 영역

| 화면 | 구성 요소 |
| --- | --- |
| 도입 화면 | 전체 화면. 도입 이미지 표시. 음성 입력 비활성화 |
| 장면 화면 | 좌: 전개 스토리 / 우: 대화 영역 2분할. 장면 이미지와 캐릭터 표시. **장면 4개가 이 화면을 재사용** |
| 말하기 후 활동 | 카드 배열 + 재구성 발화 |

### 2.2 필수 — 이야기 진행 화면 상세

프론트 작업 중 가장 복잡한 부분이다.

**전개 → 대화 순차 진행**
전개와 대화가 한 화면에 있지만 동시에 진행되지 않는다. 전개 스토리가 종료된 뒤 오른쪽 대화 영역이 활성화된다.

**문장 단위 순차 표시**
긴 텍스트를 한 번에 표시하지 않는다. 인터뷰에서 나온 요구사항이다. 도입과 전개 텍스트를 문장 단위로 분리해 순차 표시한다.

**아이 이름 치환**
캐릭터 첫 대사에 치환 자리가 있다.

- 대화1: `"ㅇㅇ아, 내 방귀가..."`
- 대화4: `"ㅇㅇ이 덕분에..."`

받침 유무에 따라 조사가 달라지므로 백엔드와 치환 주체를 합의한다. **백엔드에서 치환해 내려주는 방식을 권장한다.** 화면 텍스트와 TTS 텍스트, AI에 전달되는 텍스트가 일치해야 하기 때문이다.

**TTS 자동 재생 + 다시 듣기**
캐릭터 음성은 자동 재생한다. 아이가 매번 재생 버튼을 누르는 방식은 인터뷰에서 부정적으로 평가되었다. 다시 듣기 버튼은 별도로 제공한다.

**장면 이미지·캐릭터 표시**
도입 화면과 각 장면 화면에 이미지와 캐릭터를 표시한다. 이미지 파일은 주최측이 구글 드라이브로 제공 예정이며 아직 수령 전이다. 수령 전까지는 플레이스홀더로 진행하되, **이미지 규격(비율·해상도)을 미리 정해두면 교체가 수월하다.**

> 규격 제안과 폴백 계획은 [../spec/assets.md](../spec/assets.md)에 정리해 두었다.
> 배경은 `1280×800` 원본에 좌측 `768×800` 세이프 에어리어, 캐릭터 초상은 `320×320` 투명 PNG다.

### 2.3 필수 — 음성 대화 UI

프론트 작업의 핵심이다. 상태 전이를 명확히 관리해야 한다.

```
캐릭터 발화 재생 중
  → (발화 종료) 효과음 + 화면 변화로 "네 차례" 안내
  → 마이크 자동 활성화
  → 아이 발화 중          (녹음 중 표시)
  → STT 변환 중            (변환 중 표시)
  → 변환 텍스트 화면 표시
  → 아이가 [보내기] 클릭
  → 캐릭터 응답 대기       (대기 중 표시)
  → 캐릭터 발화 재생 중    (반복)
```

주의점:

| 항목 | 내용 |
| --- | --- |
| 마이크 활성화 시점 | 캐릭터 발화가 끝난 뒤 자동 활성화. **발화 중 활성화하면 캐릭터 음성이 녹음된다** |
| 발화 확정 방식 | 자동이 아니라 보내기 버튼. 아이가 자기 말이 제대로 입력되었는지 확인하고 보내는 구조 |
| 진행 상태 구분 | 녹음 중 / 변환 중 / 응답 대기 / 재생 중 4가지가 시각적으로 구분되어야 한다. 인터뷰에서 명시된 요구사항 |
| 대화 내역 표시 | 아이와 캐릭터를 좌우 배치 또는 색상으로 구분 |

### 2.4 필수 — 미션 화면

미션은 처음부터 노출하지 않는다. **서버가 노출 시점을 판단해 내려준다.** 프론트는 서버 응답에 미션 노출 신호가 오면 그때 표시한다.

미션은 별도 화면이 아니다. 주최측 콘텐츠 흐름 자료에 "전개·대화·미션은 각각 별도 화면이 아니라 같은 장면 화면 안에서 순차적으로 진행되는 콘텐츠 단계"로 명시되어 있다. **전체 화면 모달이나 별도 라우트로 만들지 말고**, 대화 영역 안에서 자연스럽게 이어지도록 구성한다.

| 미션 | 위치 | 내용 |
| --- | --- | --- |
| 미션1 | 대화3 (마을 이장) | 배 따기 방법 구성 |
| 미션2 | 대화4 (며느리) | 친구의 단점을 장점으로 바꾸기 |

미션 수행 결과는 아이 발화로 수집되며 다음 대화에 반영된다. 별도 입력 UI가 필요한지는 제공 자료에 명시되어 있지 않으므로 **음성 대화 흐름을 유지하는 것을 기본으로 한다.**

### 2.5 필수 — 말하기 후 활동

```
카드 무작위 배치            (요건: 4~5개 / 현재 콘텐츠: 4개)
  → 아이가 드래그로 순서 배열
  → [제출] → 서버가 정답 판정
  → 오답이면 재시도 (attempt_count 증가)
  → 정답이면 핵심 단어 표시  (요건: 3~4개 / 현재 콘텐츠: 4개)
  → 카드 + 단어 보면서 전체 이야기 음성 재구성
  → STT 변환 → 저장
```

오답 시 재시도 흐름은 `attempt_count` 컬럼이 존재한다는 점에서 도출한 것으로, 제공 자료에 명시적 규칙은 없다. **재시도 횟수 제한 여부는 팀에서 정한다.**

- **정답 판정을 프론트에서 하지 않는다.** PRD 명시 제약이다. 서버로 순서를 전송하고 결과를 수신한다
- 카드 내용은 서버가 `post_activity_config`에서 내려준다. 하드코딩하지 않는다
- 카드는 전개 이미지와 텍스트를 함께 표시한다. 이미지는 주최측 제공 자료에 포함된다

### 2.6 필수 — UX 준수사항

인터뷰에서 도출된 항목이다. 구현 시 지속 참조한다.

- 글씨 크기를 크게 한다. 저학년 대상이다
- 한 화면에 카드·그림·버튼이 동시에 나타나지 않도록 한다
- 지금 무엇을 해야 하는지가 항상 명확해야 한다
- 버튼이 여러 개 동시에 보이지 않도록 한다

### 2.7 필수 — 배포

Vercel 무료 배포. 백엔드가 Render 무료 티어이므로 **콜드 스타트**가 있다. 첫 요청이 수십 초 소요될 수 있으니 로딩 처리를 넉넉히 잡는다.

### 2.8 프론트엔드 선택 작업

| 항목 | 내용 |
| --- | --- |
| 단어장 화면 | 저장된 단어 목록, 뜻, 음성 듣기 |
| 캐릭터 마음 변화 | 아이 발화에 따라 캐릭터 표정·태도 변화 |
| 보호자 리포트 화면 | 역량 분석, 대표 발화, 학습 가이드 |
| 설정·공지사항·고객센터·이용 안내 | |

## 3. 백엔드 담당

### 3.1 필수 — DB 스키마 구축

PostgreSQL, 9개 테이블이다. 컬럼 정의는 [PRD 8장](../product/prd.md)에 전부 있다.

```
parents, children, child_consents,
stories, story_scenes,
story_sessions, messages, utterance_analyses,
post_activity_results
```

PRD에서 추가한 컬럼 2개를 누락하지 않는다.

| 컬럼 | 타입 | 용도 |
| --- | --- | --- |
| `story_scenes.scene_type` | `varchar` | `intro` / `narrative` / `dialogue` |
| `story_scenes.element_criteria` | `jsonb` | 장면별 요소 인정 기준 |

**NOT NULL 완화**도 필요하다. 원본 정의서는 대화 관련 컬럼이 전부 필수이나 도입·전개 장면에는 해당 값이 없다. `scene_type = dialogue`일 때만 필수로 둔다.

### 3.2 필수 — 콘텐츠 데이터 적재

이야기 1개, 장면 9개를 적재한다. 값은 [PRD 7장](../product/prd.md)에 전부 있다.

| 적재 대상 | PRD 위치 | 저장 위치 |
| --- | --- | --- |
| `stories` 1건 | 7.1 | DB |
| `story_scenes` 9건 (도입1 + 전개4 + 대화4) | 7.2, 7.4, 7.5 | DB |
| `conflict` 4건 | 7.5.1 | DB |
| `element_criteria` 4건 | 7.5.2 | DB |
| `preferred_turns` 4건 | 7.3 | DB |
| `post_activity_config` | 7.8 | DB |
| `remainingWorries` · `guidanceStyle` | 7.5.3 | **코드 상수** |

`remainingWorries`는 **캐릭터+장면 조합 키**로 관리한다. 며느리가 대화1과 대화4에 모두 등장하나 값이 다르다.

### 3.3 필수 — 인증

- Spring Security + JWT
- 카카오 소셜 로그인
- **Supabase를 사용하지 않는다.** 원본 정의서에 Supabase Auth 전제가 있으나 적용하지 않는다

### 3.4 필수 — 계정·아이 관리

- 보호자 계정 생성
- 아이 프로필 CRUD. 계정당 최대 3명 제한 검증
- 동의 관리. 동의가 없거나 철회된 아이는 세션 시작을 차단한다. **서버에서 막아야 한다**

### 3.5 필수 — 대화 엔진 (백엔드 작업의 핵심)

파이프라인 4단계 중 백엔드가 직접 구현하는 것은 ②③이고, ①④는 AI 서버에 위임한다.

| 단계 | 주체 | 백엔드가 할 일 |
| --- | --- | --- |
| ① 발화 분석 | AI 서버 | 입력 조립 후 호출, 결과 수신 |
| ② 서버 후처리 | 백엔드 | 직접 구현 |
| ③ 진행 판단 | 백엔드 | 직접 구현 |
| ④ 캐릭터 응답 | AI 서버 | 모드·재료 전달 후 호출, 결과 수신 |

#### ② 서버 후처리

AI가 반환한 분석 결과를 그대로 신뢰하지 않고 검증한다.

- `evidence`가 아이 발화 원문에 실제로 존재하는지 확인한다. 없으면 해당 요소를 삭제한다
- 같은 요소가 한 턴에 중복 탐지되면 하나로 정리한다
- 8개 스키마(`DECISION`, `REASON`, `PERSPECTIVE`, `SOLUTION`, `RESULT`, `EMOTION`, `EMPATHY`, `REQUEST`)에 없는 값을 제거한다

> 이 단계를 AI에 맡기지 않는다. LLM이 존재하지 않는 근거를 생성하는 것을 막는 안전장치이므로 **LLM 밖에 있어야 의미가 있다.**

#### ③ 진행 판단

아래 규칙으로 응답 모드(`NORMAL` / `GUIDED` / `CLOSING`)와 종료 여부를 확정한다. 이 판단은 전적으로 서버 규칙이며 LLM에 위임하지 않는다.

| 조건 | 결과 |
| --- | --- |
| `turnCount >= preferred_turns` AND missing 없음 | `CLOSING` / `GOAL_MET` |
| `turnCount >= max_turns` | `CLOSING` / `MAX_TURNS` |
| 첫 발화 / 신규 요소 있음 / 직전이 GUIDED | `NORMAL` 강제 |
| missing 있음 + 직전 GUIDED 아님 + (저정보 2연속 OR 신규요소없음 2연속 OR 남은턴 ≤ 2) | `GUIDED` |

보조 상태 판정:

| 상태 | 기준 |
| --- | --- |
| `turns_without_new_element` | 신규 사고 요소가 잡히지 않은 턴이 2회 연속이면 유도 |
| `consecutive_low_information_turns` | `SHORT` / `UNCLEAR` / `OFF_TOPIC`이 2회 연속이면 유도 |

`utteranceValidity`가 `VALID`여도 필수 요소가 남으면 `scene_goal_met`은 `false`일 수 있다.

**판단 순서를 지킬 것.** 순서를 바꾸면 결과가 달라진다.

```
1. 종료 조건 확인      (요소 충족+최소턴 / 최대턴 도달)
2. 강한 유도 제한 확인  (첫 발화 / 신규 요소 있음 / 직전 GUIDED)
3. 유도 필요성 확인     (missing 있음 + 정체 / 저정보 / 남은턴 부족)
4. 해당 없으면 NORMAL
```

누적 계산:

```
accumulatedElements = 기존 ∪ 이번 턴 detectedElements의 type
missingElements     = requiredElements − accumulatedElements
```

`missingElements`는 DB에 저장하지 않고 매번 계산한다.

#### ④ CLOSING은 AI를 호출하지 않는다

`CLOSING`으로 판정되면 AI 서버를 호출하지 않고 `story_scenes.character_closing`을 조회해 그대로 `messages`에 저장하고 응답한다. **검수된 고정 텍스트이므로 LLM이 관여하면 안 된다.**

#### 반응 원칙 키 매핑

AI에 전달할 `reactionKey`를 백엔드가 결정한다.

| 조건 | `reactionKey` |
| --- | --- |
| `PLAYFUL` / `OFF_TOPIC` | `playfulUtterance` |
| `QUESTION` | `questionFromChild` |
| `SOLUTION` | `proposalFromChild` |
| `SHORT` / `UNCLEAR` | `unclearUtterance` |
| `EMPATHY` | `empathyFromChild` |
| 의견·반박·결정 | `disagreement` |
| 그 외 | `directResponse` |

`SOLUTION`이 `SHORT`보다 우선한다.

#### 유도 대상 선택

`GUIDED`일 때 아직 충족되지 않은 필수 요소 중 하나를 고른다. 선택 원칙은 [PRD 6.9](../product/prd.md)를 따른다.

- 아직 충족되지 않은 필수 요소를 우선
- 직전에 유도한 요소를 반복하지 않을 것 (`last_guidance_target` 확인)
- 아이가 방금 말한 내용과 자연스럽게 이어지는 요소를 우선

#### 유도 재료 구성

고른 요소로 `remainingWorries[guidanceTarget]`을 조회해 AI에 전달한다. 해당 요소에 worry가 없으면 **아무것도 전달하지 않는다.** 대체 문구를 생성해 넣지 않는다. PRD 명시 규칙이다.

### 3.6 필수 — 세션 상태 관리

`story_sessions`가 상태 머신 역할을 한다. 매 턴 갱신할 필드:

| 필드 | 갱신 규칙 |
| --- | --- |
| `current_scene_id` | 현재 장면 |
| `current_child_turn_count` | +1 |
| `accumulated_elements` | 합집합 갱신 |
| `last_detected_elements` | 이번 턴 결과로 교체 |
| `last_response_mode` | `NORMAL` / `GUIDED` / `CLOSING` |
| `last_guidance_target` | 유도 대상 요소 |
| `turns_without_new_element` | 신규 요소 없으면 +1, 있으면 0 |
| `consecutive_low_information_turns` | `SHORT`/`UNCLEAR`/`OFF_TOPIC`이면 +1, 아니면 0 |
| `scene_goal_met` | missing이 비었으면 `true` |
| `scene_end_reason` | `GOAL_MET` / `MAX_TURNS` |
| `last_activity_at` | 현재 시각 |

장면 전환 시 초기화할 필드: `current_child_turn_count`, `accumulated_elements`, `turns_without_new_element`, `consecutive_low_information_turns`, `scene_goal_met`, `scene_end_reason`

> 초기화하지 않으면 다음 장면이 이전 장면의 요소를 물려받아 첫 턴에 즉시 종료된다.
> 다만 이 초기화 규칙은 제공 자료와 PRD에 명시되어 있지 않은 **팀 판단 사항**이다.
> `accumulated_elements`가 "현재 장면에서 누적 확인된 사고 요소"로 정의되어 있고
> `required_elements`가 장면별로 다르다는 점에서 도출했다.

### 3.7 필수 — 미션 노출 판정

미션 노출 시점은 **백엔드가 결정한다. AI가 정하지 않는다.**

미션1 노출 조건 (하나라도 해당):

- 아이가 며느리의 방귀를 활용할 수 있다고 제안한 경우
- 해결 방향은 나왔으나 방법이 구체적이지 않은 경우
- 2회 이상 대화했으나 실행 방법이 나오지 않은 경우
- 캐릭터 질문만으로 해결 방법을 구체화하기 어려운 경우

**중복 노출 방지**: 노출 시 `messages`에 `speaker_type = system` 메시지를 1건 저장한다. 다음 턴에 해당 `scene_id`에 system 메시지가 존재하면 재노출하지 않는다.

### 3.8 필수 — 말하기 후 활동

- **카드 순서 정답 판정을 서버에서 계산한다.** 프론트 판정을 허용하지 않는다
- `stories.post_activity_config`에서 정답 순서를 조회한다
- `attempt_count`를 누적한다
- 정답 시 `retelling_keywords`를 응답한다
- `post_activity_results`를 저장한다. 세션당 1건

### 3.9 필수 — 데이터 처리 제약

- 원본 음성 파일을 저장하지 않는다
- STT 실패로 확정 텍스트가 없으면 메시지를 생성하지 않는다
- `stt_raw_text`는 아이 발화에만 저장한다
- 캐릭터 고정 첫 대사와 마지막 대사도 재생 시점에 `messages`에 저장한다

### 3.10 필수 — 아이 이름 치환

`ㅇㅇ아` / `ㅇㅇ이` 치환은 **백엔드에서 수행할 것을 권장한다.** 프론트와 TTS 양쪽에 동일한 텍스트가 전달되어야 하는데, 프론트에서 치환하면 AI에 전달되는 텍스트와 화면 텍스트가 달라진다.

### 3.11 필수 — 배포

Render 무료 티어. **15분 무활동 시 슬립되며 콜드 스타트에 수십 초가 소요된다.** AI 서버도 무료 티어를 사용하면 홉이 두 개가 되어 더 느려진다. 시연 직전 워밍업 요청을 미리 전송할 것을 권장한다.

> 관련: [화면 명세 C-6](../spec/screens.md)의 15초 타임아웃이 콜드 스타트와 충돌할 수 있다.

## 4. AI 담당

AI 서버는 **엔드포인트 2개만** 구현한다. DB 접근이 없고 상태를 갖지 않는다. 수신한 JSON만 보고 응답한다.

> 아래 JSON 스키마는 **제안**이다. PRD는 입력·출력에 담길 항목만 정의하고 있으며 필드명과 구조는
> 확정되어 있지 않다. 백엔드와 합의한 뒤 확정한다.
> 단, `childIntent` / `detectedElements[].type` / `utteranceValidity`의 **허용 값 목록은 PRD 확정 사항**이므로
> 변경하지 않는다.

### 4.1 필수 — 엔드포인트 1: 발화 분석

**입력**

```json
{
  "sceneContext": "장면 설명 + conflict를 합친 텍스트",
  "goal": "장면 학습 목표",
  "previousCharacterMessage": "직전 캐릭터 발화 또는 null",
  "childUtterance": "아이 최신 발화",
  "targetElements": ["PERSPECTIVE", "EMOTION", "REASON", "SOLUTION"],
  "elementCriteria": {
    "PERSPECTIVE": "이 장면에서 인정할 기준",
    "EMOTION": "이 장면에서 인정할 기준"
  }
}
```

**출력**

```json
{
  "childIntent": "REASONING",
  "mainPoint": "아이 말의 핵심 뜻",
  "detectedElements": [
    { "type": "PERSPECTIVE", "evidence": "창피해서 계속 참았어요" }
  ],
  "utteranceValidity": "VALID"
}
```

**허용 값**

| 필드 | 허용 값 |
| --- | --- |
| `childIntent` | `QUESTION`, `OPINION`, `REASONING`, `SOLUTION`, `DECISION`, `PERSPECTIVE`, `EMOTION`, `REQUEST`, `CHALLENGE`, `PLAYFUL`, `OFF_TOPIC`, `SHORT_RESPONSE`, `UNCLEAR` |
| `detectedElements[].type` | `DECISION`, `REASON`, `PERSPECTIVE`, `SOLUTION`, `RESULT`, `EMOTION`, `EMPATHY`, `REQUEST` — **8개뿐이다.** 다른 값을 생성하지 않는다 |
| `utteranceValidity` | `VALID`, `SHORT`, `UNCLEAR`, `OFF_TOPIC`, `PLAYFUL` |

**프롬프트 설계 시 반드시 지킬 것**

- `evidence`는 아이 발화에 **실제로 존재하는 문자열**이어야 한다. 백엔드가 원문 대조 검증을 수행하며, 일치하지 않으면 해당 요소를 폐기한다. **요약하거나 다듬으면 결과가 통째로 사라진다**
- 아이가 말하지 않은 이유·감정·의도를 추론해 추가하지 않는다
- `targetElements`는 정답 목록이 아니다. 해당 요소가 실제로 나타났을 때만 포함한다
- `elementCriteria`를 판정에 반드시 반영한다. 같은 `REASON`이라도 장면마다 인정 기준이 다르다
- 막연한 당위 표현("잘해줘야 해요", "그러면 안 돼요")은 요소로 인정하지 않는다
- **JSON만 출력한다.** 마크다운 코드펜스나 설명 문장을 포함하지 않는다

**입력에 포함되지 않는 값**

이야기 제목, 캐릭터 이름, 누적 요소, 턴 카운트는 의도적으로 제외했다. 분석이 "지금 이 발화"만 보도록 하기 위한 설계이므로 요구하지 않는다.

### 4.2 필수 — 엔드포인트 2: 캐릭터 응답 생성

**입력**

```json
{
  "characterName": "며느리",
  "characterPersona": "조심스럽고 걱정이 많은 말투",
  "sceneContext": "장면 설명 + conflict",
  "previousCharacterMessage": "직전 캐릭터 발화",
  "childUtterance": "아이 최신 발화",
  "analysis": { "childIntent": "...", "mainPoint": "..." },
  "responseMode": "GUIDED",
  "reactionKey": "proposalFromChild",
  "guidanceTarget": "REASON",
  "remainingWorry": "왜 꼭 말해야 하는지 나는 아직 잘 모르겠어."
}
```

**출력**

```json
{ "text": "캐릭터 대사" }
```

#### responseMode별 동작

| 모드 | 동작 |
| --- | --- |
| `NORMAL` | 아이 말에 자연스럽게 반응한다. **장면을 닫지 않는다** |
| `GUIDED` | `remainingWorry`를 대사에 녹여 부족한 요소를 유도한다 |

`CLOSING`은 전달되지 않는다. 백엔드가 고정 대사를 사용하므로 **호출 자체가 발생하지 않는다.**

#### reactionKey별 반응 원칙

| `reactionKey` | 반응 방식 |
| --- | --- |
| `playfulUtterance` | 장난을 실제 사건으로 단정하지 않고 받아친다 |
| `questionFromChild` | 질문에 먼저 답한다 |
| `proposalFromChild` | 제안의 좋은 점을 인정하고 걱정을 하나만 제시한다 |
| `unclearUtterance` | 필요할 때만 짧게 되묻는다 |
| `empathyFromChild` | 공감으로 반응한다 |
| `disagreement` | 무조건 부정하지 않고 걱정을 하나 제시한다 |
| `directResponse` | 최신 말에 직접 반응한다 |

#### 프롬프트 설계 시 반드시 지킬 것

- **캐릭터를 유지한다.** 며느리는 조심스럽고, 시아버지는 완고하며, 이장은 사람이 좋다. 안내자나 교사처럼 말하지 않는다. 인터뷰에서 캐릭터가 아이 의견에 바로 동의하지 않고 자기 입장을 유지할 때 아이가 다시 생각한다는 결과가 나왔다
- **평가하지 않는다.** "잘했어요", "정답이에요" 같은 표현을 사용하지 않는다. 아이 말을 채점하는 것이 아니라 대화하는 것이다
- 7세~초2 수준 어휘를 사용하고 문장을 짧게 유지한다
- **`NORMAL`에서 장면을 닫지 않는다.** "그럼 그렇게 할게" 같은 마무리 톤이 나오면 대화가 남았는데 종료된 느낌을 준다
- `remainingWorry`가 없으면 교육용 문구를 생성하지 않는다. 일반 반응으로 처리한다
- **아이 이름은 백엔드가 이미 치환해 전달한다.** 별도로 처리하지 않는다

> 캐릭터별 성격 원문은 [../reference/characters.md](../reference/characters.md),
> 장면별 `remainingWorries`·`guidanceStyle` 값은 [PRD 7.5.3](../product/prd.md)에 있다.

### 4.3 필수 — 모델·비용 제약

- `gpt-5-mini`를 사용한다
- 세션 8턴 기준 **1.5만~2만 토큰**을 초과하지 않는다. 주최측이 정한 상한이다
- 프롬프트가 길어지면 이 예산이 초과된다. **시스템 프롬프트를 간결하게 유지한다**

### 4.4 필수 — 튜닝

**값을 작성하는 것보다 맞추는 것이 실제 작업이다.**

- `elementCriteria`가 느슨하면 아무 발화나 통과해 장면이 1~2턴에 종료된다
- 지나치게 엄격하면 아이가 `max_turns`까지 유도만 받다가 종료된다
- 아이 발화 샘플을 작성해 반복 실행하고 기준 문구를 조정한다
- 조정 결과는 백엔드에 전달해 **DB의 `element_criteria`를 갱신**한다

> 초기값은 [PRD 7.5.2](../product/prd.md)에 팀이 작성해 둔 것이 있다.
> [PRD 7.5.4](../product/prd.md)도 "실제 발화 샘플로 검증한 뒤 조정하는 것을 전제로 한다"고 명시한다.

### 4.5 AI 선택 작업

| 항목 | 내용 |
| --- | --- |
| 보호자 리포트 분석 | 어휘·논리·표현 3축 분석 |
| 대표 발화 추출 | 세션 중 인상적인 발화 선별 |
| 단어 쉬운 뜻 생성 | 아이 수준 설명 + 이야기 속 문장 |
| 캐릭터 감정 상태 산출 | 표정 변화용 |

## 5. 백엔드 ↔ AI 계약

> 📌 1장의 "백엔드↔AI 계약 — **8장 참조**"는 이 5장을 가리킨다. 문서 내부 참조 오류다.
> 8장은 담당별 선택 항목 요약이다.

백엔드 담당이 중간 조율 역할을 맡으므로 이 부분을 주도한다. **코딩 착수 전에 AI 담당과 합의한다.**

| 항목 | 정해야 할 것 |
| --- | --- |
| 프로토콜 | REST / JSON 고정 |
| 엔드포인트 경로 | 예: `POST /analyze`, `POST /respond` |
| 인증 | 내부 호출용 고정 토큰 수준이면 충분 |
| 타임아웃 | 백엔드가 대기할 시간 |
| 실패 시 백엔드 동작 | 재시도 횟수, 최종 실패 시 응답 내용 |
| 배포 주소 | AI 서버 URL |

**타임아웃과 실패 처리를 반드시 정한다.** 한 턴에 AI 호출이 두 번(분석 + 응답) 발생한다.
각 5초씩만 잡아도 10초이며, 여기에 STT와 콜드 스타트가 더해진다.
AI 서버 장애 시 아이 화면이 무한 로딩에 빠지지 않도록 백엔드가 방어해야 한다.

> ⚠️ [화면 명세 C-6](../spec/screens.md)의 프론트 타임아웃은 **15초**다.
> AI 10초 + STT + 콜드 스타트를 더하면 이 예산을 넘긴다. → [../open-questions.md](../open-questions.md) Q-14

### 계약 확정 전에도 진행 가능한 작업

| 담당 | 작업 |
| --- | --- |
| 백엔드 | 스키마 구축, 콘텐츠 적재, 인증, 계정 관리, ②③ 규칙 엔진 |
| AI | 프롬프트 초안, 로컬에서 샘플 발화로 분석 품질 확인 |
| 프론트 | 정적 화면, UI 컴포넌트, 상태 전이 로직 |

계약이 확정되면 백엔드가 **AI 서버를 목(mock)으로 먼저 연결**해 진행할 것을 권장한다.
고정 JSON을 반환하는 스텁이면 충분하다. AI 서버 완성을 기다리지 않고 전체 흐름을 검증할 수 있다.
