## 1. 서비스 개요

### 1.1 서비스 정의 (주최측)

굿퀘스천은 아이가 동화 속 캐릭터와 음성으로 대화하며 말하기 능력을 기르는 서비스다. 시스템은 아이의 발화에서 사고 요소를 분석하고, 장면별 목표에 비추어 부족한 요소를 캐릭터의 질문으로 자연스럽게 유도한다.

### 1.2 서비스명과 의미 (주최측)

서비스명 "굿퀘스천"은 답보다 질문이 더 중요한 시대에, 아이가 좋은 질문을 던질 수 있도록 서비스가 아이에게 좋은 질문들을 묻겠다는 의미를 담는다. **상표권 등록이 완료된 이름으로 변경할 수 없다.**

### 1.3 로고 (주최측)

기존 로고는 말풍선 모양과 Question의 Q를 형상화하여 제작되었으며 서비스 자료에 사용 중이다. 이번 해커톤에서는 더 나은 제안이 있을 경우 변경할 수 있다.

### 1.4 디자인 방향 (주최측)

- 아이에게는 친근하고 즐거운 놀이 공간처럼 느껴질 것
- 학부모에게는 신뢰할 수 있는 교육 서비스로 보일 것
- 따뜻하고 밝은 톤
- 지나치게 유아적이거나 장난감처럼 보이지 않는 정돈된 느낌
- 아이가 편안하게 대화할 수 있는 포근함

## 2. 목표 사용자

### 2.1 사용자 구분 (주최측)

| 구분 | 설명 |
| --- | --- |
| 보호자 | 계정을 생성하고 아이 프로필을 등록·관리하는 사용자 |
| 아이 | 이야기 활동을 실제로 수행하는 사용자 |

### 2.2 대상 연령 (주최측)

주최측이 2026년 10월 진행 예정인 테스트의 대상은 **7세, 초등학교 1학년, 초등학교 2학년**이다. 제공된 콘텐츠의 `scene_description`과 고정 대사는 해당 연령 기준으로 자문위원 난이도 검수가 완료된 상태다.

### 2.3 비즈니스 모델 (주최측 · 참고)

보호자 계정 기준으로 아이 1명일 때 34,000원, 1명 추가 시 비용이 더해지는 구독 방식을 검토 중이다. 세부 구독료는 10월 테스트를 통해 확정 예정이다. **본 MVP의 구현 범위에는 결제 기능이 포함되지 않는다.**

## 4. 기능 요건

### 4.1 필수 요건 (주최측)

#### F-01. 회원가입 및 아이 등록

보호자가 가입하고 서비스를 이용할 아이를 등록한다.

- 이메일 또는 소셜 로그인 (카카오, 구글, 네이버 중 1개 이상 제공)
- 보호자 계정 아래 여러 아이 프로필 등록 가능
- 아이 이름, 나이 등록

**수집 정보** (주최측 확정):

| 대상 | 항목 |
| --- | --- |
| 학부모 | 소셜 로그인 계정 식별값, 이메일 |
| 아이 | 서비스 내에서 불릴 이름, 나이(만) |

**계정당 아이 등록 수: 최대 3명** (팀 결정 — 주최측은 최대 3명 지원 계획이며 테스트 단계에서는 1명 등록을 기본으로 제안했으나, 팀은 최대 3명 지원으로 구현한다)

#### F-02. 메인 화면

아이가 다음 활동을 바로 시작할 수 있게 한다.

- 진행 중인 이야기 표시와 이어하기 버튼 제공
- 추천 이야기 2~3개 표시
- 홈, 이야기, 단어장, 마이페이지 표시

> 비고: 추천 로직은 미구현 상태이며, 홈 화면 UI 구성을 위해 영역만 우선 배치한다.

#### F-03. 이야기 선택

아이가 이야기를 선택하고 활동 내용을 확인한다.

- 이야기 목록에 대표 이미지, 제목, 예상 시간, 주요 주제 표시
- 이야기 선택 시 상세 화면으로 이동
- 상세 화면에 이야기 도입, 상황, 아이 역할 표시
- 주제별 필터링 제공

**상세 화면 표시 항목 정의** (주최측):

| 항목 | 내용 |
| --- | --- |
| 이야기 도입 | 장면 구성 테이블의 도입 `scene_description` 내용 |
| 이야기 상황 | 큰 방귀 때문에 며느리가 집에서 쫓겨날 위기에 놓였어요. |
| 아이 역할 | 며느리의 방귀가 특별한 장점이 될 수 있도록 도와주세요. |

> 이야기 상황과 아이 역할은 팀에서 내용 변경이 가능하다.

#### F-04. 이야기 장면 진행

이야기 장면을 보여주고 캐릭터가 질문한다.

- 장면 이미지와 캐릭터 표시
- 상황 설명과 캐릭터 대사 제공
- 캐릭터 음성 자동 재생
- 캐릭터 대사 다시 듣기 제공

> 캐릭터 음성은 제공되는 음성 파일이 아니라 **TTS**를 사용한다 (주최측 확정).

#### F-05. 아이 음성 대화

아이가 캐릭터의 질문에 음성으로 답변한다.

- 캐릭터 발화 종료 후 마이크 자동 활성화
- 음성 입력 시작
- 아이 음성을 텍스트로 변환 (STT)
- 아이가 말을 마친 뒤 보내기 버튼을 눌러 발화를 제출
- 변환된 텍스트를 화면에 표시
- 아이와 캐릭터의 대화 내역 구분 표시
- 아이 발화 원문을 세션에 저장

> 비고: 캐릭터 발화가 끝나면 효과음과 화면 변화를 통해 아이가 말할 차례임을 안내한다.

#### F-06. 발화 분석 및 캐릭터 반응

아이의 답변을 분석해 캐릭터 반응과 다음 진행을 결정한다.

- 보내기 버튼을 누르면 확정된 발화 텍스트를 저장하고 분석
- 발화에서 생각, 이유, 감정, 관점, 판단, 해결 방법 등의 사고 요소를 추출한 뒤 현재 장면의 목표 발화 조건과 비교
- 목표가 부족하면 캐릭터의 성격과 입장을 유지한 추가 질문을 생성
- 목표를 충족하거나 최대 대화 횟수에 도달하면 다음 장면으로 이동
- 마지막 장면 완료 후 전체 대화와 분석 결과를 저장
- 말하기 후 활동으로 전환

> 상세 규칙은 본 문서 6장을 따른다.

#### F-07. 말하기 후 활동

주요 장면의 순서를 맞춘 뒤 핵심 단어를 활용해 이야기를 다시 말한다.

- 주요 장면 카드 4~5개를 무작위로 제시
- 아이가 카드를 이야기 순서대로 배열
- 배열 순서가 정답일 시, 핵심 단어 3~4개 제공
- 카드와 단어를 참고해 전체 이야기를 음성으로 재구성
- 텍스트로 전환 및 표시
- 발화 내용과 활동 완료 여부 저장

> 재구성 주체는 아이다. **정답 여부는 프런트엔드가 아니라 서버에서 계산한다.**

### 4.2 추가 요건 (주최측 · 후순위)

| ID | 요건 | 내용 | 비고 |

## 5. 서비스 흐름

### 5.1 전체 실행 흐름 (주최측)

| 단계 | 영역 | 흐름 |
| --- | --- | --- |
| 1 | 서비스 진입 및 사용자 관리 | 앱 실행 → 로그인 → 아이 선택 → 홈 화면 / 앱 실행 → 회원가입 → 보호자 계정 생성 → 아이 프로필 등록 → 아이 선택 → 홈 화면 |
| 2 | 홈 화면 및 이야기 탐색 | 홈 화면 → 이어하기 / 추천 이야기 → 이야기 상세 / 이야기 목록 → 이야기 상세 |
| 3 | 이야기 학습 진행 | 이야기 목록 → 이야기 상세 → 도입 화면 → 장면 1 → 장면 2 → 장면 3 → 장면 4 → 후속 활동 화면 |
| 4 | 보호자 리포트 | 보호자 리포트 → 말하기 역량 분석 / 대표 발화 확인 / 가정 학습 가이드 |
| 5 | 설정 및 기타 | 설정 / 공지사항 / 고객센터 / 이용 안내 / 로그아웃 |

> 이어하기는 이야기 상세를 거치지 않고 도입 화면 이후 지점으로 직접 진입한다.

### 5.2 이야기 화면 구조 (주최측)

| 화면 순서 | 화면 유형 | 화면 구성 | 포함 콘텐츠 | 종료 조건 | 다음 화면 |
| --- | --- | --- | --- | --- | --- |
| 1 | 도입 화면 | 패드 전체 화면 | 도입 스토리 | 도입 내레이션 종료 | 장면1 화면 |
| 2 | 장면1 화면 | 왼쪽: 전개1 / 오른쪽: 대화1 | 전개 스토리 → 캐릭터 대화 | 대화1 완료 | 장면2 화면 |
| 3 | 장면2 화면 | 왼쪽: 전개2 / 오른쪽: 대화2 | 전개 스토리 → 캐릭터 대화 | 대화2 완료 | 장면3 화면 |
| 4 | 장면3 화면 | 왼쪽: 전개3 / 오른쪽: 대화3 | 전개 스토리 → 캐릭터 대화 → 미션1 | 대화3 완료 | 장면4 화면 |
| 5 | 장면4 화면 | 왼쪽: 전개4 / 오른쪽: 대화4 | 전개 스토리 → 캐릭터 대화 → 미션2 | 대화4 완료 | 말하기 후 활동 또는 이야기 종료 |

- 도입 화면에서는 캐릭터 대화 영역을 노출하지 않고 아이의 음성 입력 기능을 비활성화한다. 도입 내용은 한 문장씩 순차 표시하거나 음성으로 재생한다.
- 전개와 대화는 하나의 화면에 배치되지만 **동시에 진행하지 않는다.** 전개 스토리가 종료된 뒤 대화 영역이 활성화된다.

**콘텐츠 계층 구조** (주최측):

```
이야기 진행 ─┬─ 도입 화면   → 도입 스토리
             ├─ 장면1 화면  → 전개1 · 대화1
             ├─ 장면2 화면  → 전개2 · 대화2
             ├─ 장면3 화면  → 전개3 · 대화3 · 미션1
             └─ 장면4 화면  → 전개4 · 대화4 · 미션2

이야기 완료 ─── 후속 활동 화면 → 이야기 재구성
```

> 전개·대화·미션은 각각 별도 화면이 아니라, 같은 장면 화면 안에서 순차적으로 진행되는 콘텐츠 단계다.
> **미션을 별도 화면이나 전체 화면 모달로 구성하지 않는다.**

### 5.3 UX/UI 참고사항 (주최측 · 고객 인터뷰 기반)

실제 인터뷰와 테스트에서 확인된 아동·보호자 사용 특성이다. MVP 화면 설계 시 반영한다.

| 항목 | 참고사항 |
| --- | --- |
| 텍스트와 정보량 | 저학년 아동에게 긴 텍스트, 작은 글씨, 복잡한 화면 구성은 인지 부담이 될 수 있다 |
| 콘텐츠 제시 방식 | 긴 설명을 한 번에 보여주기보다 한 문장씩 단계적으로 제시하는 방식이 이해에 도움이 될 수 있다 |
| 화면 집중도 | 저학년과 언어 수준이 낮은 아동은 화면에 정보가 많을수록 현재 무엇을 해야 하는지 놓칠 가능성이 있다 |
| 말하기 타이밍 | 캐릭터의 말이 끝난 뒤 아이가 말해야 하는 시점을 시각적·청각적으로 명확하게 알려줄 필요가 있다 |
| 진행 상태 | 아이 발화 중, 음성 변환 중, 캐릭터 응답 대기 등 현재 진행 상태가 분명하게 구분될 필요가 있다 |
| STT 확인 | 아이가 자신의 말이 제대로 입력되었는지 알 수 있도록 STT 변환 결과를 화면에서 확인할 수 있으면 좋겠다는 의견이 있었다 |
| 음성 재생 | 캐릭터 음성을 아이가 매번 직접 재생하기보다 자동으로 재생하는 방식이 사용 흐름에 더 적합하다는 의견이 있었다 |
| 조작 복잡도 | 저연령 아동은 여러 버튼이나 기능이 동시에 보일 경우 조작에 어려움을 느낄 수 있어, 현재 단계에서 필요한 행동이 분명하게 보여야 한다 |

**핵심 정리** (주최측):

- 저학년 아동이 화면을 해석하는 데 힘을 쓰지 않고, 캐릭터의 말을 듣고 자신의 생각을 말하는 데 집중할 수 있어야 한다
- 화면의 구체적인 구성보다 대화 순서, 현재 상태, 다음 행동이 명확하게 인지되는지가 중요하다
- 캐릭터는 안내자가 아니라 실제 대화 상대처럼 느껴질 때 아동의 재발화와 몰입을 더 잘 이끌어낼 수 있다

### 5.4 추후 콘텐츠 관련 참고사항 (주최측 · MVP 범위 밖)

| 항목 | 참고사항 |
| --- | --- |
| 대화 상대성 | 캐릭터가 아이의 의견에 바로 동의하지 않고 자신의 입장을 유지할 때, 아이가 다시 생각하고 설명하려는 모습이 확인되었다 |
| 힌트 제공 | 질문에 바로 답하기 어려운 아동을 위해 상황 단서나 간단한 힌트를 제공할 필요가 있다 |
| 힌트 수준 | 힌트는 정답을 직접 알려주기보다 아이가 생각을 시작할 수 있도록 돕는 수준이 적절하다 |
| 캐릭터 몰입 | 캐릭터와의 역할극은 아동의 몰입을 높이는 데 긍정적이었으며, 캐릭터의 반응과 감정이 대화 흐름 안에서 자연스럽게 드러나는 것이 중요하다 |
| 난이도 차이 | 아동마다 학년과 언어 수준의 차이가 커, 같은 이야기라도 텍스트와 질문의 난이도를 조절할 가능성을 고려할 필요가 있다 |
| 이야기 재구성 | 이야기 종료 후 주요 장면을 다시 확인하고 순서를 맞추는 활동은 이야기 이해와 재구성에 도움이 될 수 있다는 의견이 있었다 |
| 보호자 정보 | 보호자는 점수나 복잡한 분석보다 아이가 실제로 어떤 말을 했고 어떤 부분을 잘 표현했는지 쉽게 확인하기를 원했다 |

### 5.5 인터뷰 주요 의견 (주최측 · 참고)

주최측은 인터뷰 의견 중 서비스 방향성·MVP 범위·개발 난이도와 맞지 않는 내용도 포함되어 있으므로 모든 내용을 필수 요구사항으로 해석할 필요는 없다고 안내했다.

| 영역 | 주요 요구 |
| --- | --- |
| 저학년·다문화 아동 화면 개선 | 글씨 크기 확대, 긴 말풍선을 한 문장씩 분리, 한 화면에 카드·그림·버튼이 동시에 나타나지 않도록 구성, 지금 무엇을 해야 하는지 쉽게 인지 |
| 음성 대화 흐름 | 캐릭터 음성 자동 재생, 캐릭터 발화 후 아이 답변으로 자연스러운 연결, 다시 듣기·다시 말하기 기능, 1:1 대화 방식 |
| 답변 도움 기능 | 단계적 힌트 제공, 선택지나 그림으로 답 시작, 힌트창, 힌트 요정 같은 별도 캐릭터, 터치·드래그 방식 활용 |
| 난이도 구분 | 학년별 질문 난이도·표현 수준 구분, 기초·심화 단계 선택, 저학년 어휘 사용, 어려운 단어 설명 제공 |
| 인성·관계 주제 콘텐츠 | 우정·배려·협력·공감 주제 분류, 친구의 단점을 긍정적으로 보는 활동, 갈등 해결·사과·관계 회복 콘텐츠, 교사가 수업 목적 키워드로 검색 |
| 종합 말하기 단계 | 배경·인물·사건·행동·결과를 순서대로 말하기, 순서 카드나 마인드맵 제공, 반복 사용에 따른 변화 확인 |
| 어휘 학습 | 어려워한 단어 저장, 세션 종료 후 복습, 대화 중 언제든 뜻 확인, 개인 단어장 |
| 짧은 부가 콘텐츠 | 이야기 순서 맞추기, 등장인물 감정 고르기, 의성어·의태어 활동, 친구의 장점 찾기, 다른 결말 만들기, 이야기 한 문장 정리, 장면 속 문제 찾기 |
| 보상 구조 | 별가루 수집, 동물·장식 아이템 수집, 행성 꾸미기 |
| 리포트 | 아이가 실제로 한 말 표시, 말하기·논리력 변화 추이, 여러 세션 누적, 보호자가 이해할 수 있는 지표, 잘한 부분과 연습할 부분 병기, 후속 대화 질문 제공 |

**MVP 필수 요건에 이미 반영된 항목**: 캐릭터 음성 자동 재생, 다시 듣기, 1:1 대화, 이야기 순서 맞추기, 종합 말하기 단계(말하기 후 활동), 친구의 단점을 장점으로 바꾸는 활동(미션2).
**추가 요건에 대응하는 항목**: 어휘 학습(단어 저장), 리포트(보호자 리포트), 캐릭터 감정 표현(캐릭터 마음 변화).

## 6. 대화 엔진 명세

### 6.1 전체 처리 구조 (주최측)

```
아이 최신 발화
    │
    ▼
① 발화 분석 모듈       (LLM 사용)
    · 아이 최신 발화의 의도 분석
    · 사고 요소 탐지
    · 발화 유효성 판정
    │
    ▼
② 서버 후처리 모듈     (LLM 미사용)
    · 원문 근거 검증
    · 중복 요소 정리
    · 과도하거나 약한 탐지 보정
    │
    ▼
③ 진행 판단 모듈       (LLM 미사용)
    · 현재까지 누적된 사고 요소 확인
    · 부족한 필수 요소 확인
    · 대화 정체 및 저정보 발화 확인
    · NORMAL / GUIDED / CLOSING 결정
    │
    ▼
④ 유도 정보 구성
    · 필요한 경우 유도 대상 요소 선택
    · 요소에 대응하는 캐릭터의 걱정 정보 전달
    │
    ▼
⑤ 캐릭터 응답
    · NORMAL 또는 GUIDED: 캐릭터 모델 호출
    · CLOSING: 장면별 종료 처리
```

| 단계 | 담당 모듈 | LLM 사용 | 주요 역할 |
| --- | --- | --- | --- |
| 발화 분석 | 분석 모델 | 사용 | 사고 요소와 원문 근거 추출 |
| 후처리 | 서버 코드 | 미사용 | 근거·중복·약한 탐지 검증 |
| 진행 판단 | 규칙 엔진 | 미사용 | 모드, 종료 여부, 유도 대상 결정 |
| 캐릭터 응답 | 캐릭터 모델 | 사용 | 캐릭터 대사 생성 |
| 장면 종료 | 서버 또는 콘텐츠 설정 | 미사용 | 고정된 종료 처리 실행 |

> **핵심 원칙**: 분석 LLM은 판단하지 않고 제안만 하며, 장면 목표 충족·응답 모드·종료 이유의 최종 확정은 서버 규칙이 수행한다.

**모듈별 책임 분리** (주최측) — 대화 구조는 분석, 진행, 표현을 분리한다.

발화 분석 모듈이 판단하는 것:
- 아이가 이번 발화에서 무엇을 하려는지
- 어떤 사고 요소가 직접 드러났는지
- 해당 사고 요소의 원문 근거가 무엇인지
- 발화가 정상적인 정보 발화인지, 짧거나 불명확한 발화인지

진행 판단 모듈이 결정하는 것:
- 현재 대화를 일반적으로 이어갈지
- 부족한 사고 요소를 유도할지
- 장면을 종료할지
- 유도가 필요할 경우 어떤 요소를 대상으로 할지

캐릭터 응답 모듈이 전달받는 것은 6.12를 따른다.

### 6.2 단계별 시스템 동작 (주최측)

| 단계 | 처리 내용 | 저장 위치 |
| --- | --- | --- |
| 1 | 현재 세션과 장면을 조회하고, 캐릭터의 고정 첫 대사를 불러온다 | `story_sessions`, `story_scenes` |
| 2 | 첫 대사를 화면과 음성으로 제공하고 아이의 말하기 차례를 안내한다 | `messages` |
| 3 | 아이의 음성을 글자로 변환해 화면에 보여준다. 원본 음성은 저장하지 않는다 | — |
| 4 | 아이가 확인한 문장을 최종 발화로 저장한다 | `messages` |
| 5 | 장면 상황과 직전 대사, 장면 목표, 아이의 최신 발화를 함께 분석한다 | LLM 호출 |
| 6 | 아이의 말에서 새롭게 확인된 생각 요소를 기존 기록에 추가한다 | `utterance_analyses`, `story_sessions` |
| 7 | 목표 달성 여부와 남은 대화 횟수를 바탕으로 일반 반응, 자연스러운 유도, 장면 마무리 중 하나를 결정한다 | 서버 로직 |
| 8 | 결정된 방식에 따라 캐릭터의 다음 대사를 만들고 저장한다. 장면이 끝나면 완료 상태로 변경한다 | `messages`, `story_sessions` |

### 6.3 사고 요소 분류 체계 (주최측)

| 요소 | 의미 |
| --- | --- |
| `DECISION` | 선택하거나 자신의 입장을 정함 |
| `REASON` | 판단, 의견, 선택, 요청 등의 까닭을 말함 |
| `PERSPECTIVE` | 다른 인물의 상황이나 입장을 고려함 |
| `SOLUTION` | 문제를 줄이거나 해결할 구체적인 행동과 방법을 제시함 |
| `RESULT` | 행동이나 상황 이후의 결과를 설명하거나 예상함 |
| `EMOTION` | 자신이나 다른 인물의 감정을 직접 표현함 |
| `EMPATHY` | 다른 사람의 감정이나 어려움을 이해하고 배려함 |
| `REQUEST` | 특정 상대에게 행동, 말, 태도의 변화를 요구함 |

**허용 값은 위 8개로 한정한다.**

### 6.4 기본 판정 원칙 (주최측)

- 최신 아이 발화에서 직접 확인되는 요소만 탐지한다
- 아이가 말하지 않은 이유, 감정, 의도, 결과를 추론하여 추가하지 않는다
- 각 요소에는 아이 발화에 실제로 존재하는 원문 근거가 필요하다
- 같은 표현이 여러 사고 요소를 직접 충족하면 복수 탐지가 가능하다
- 장면 목표와 무관한 사고 요소는 목표 달성 요소로 사용하지 않는다
- 막연한 당위나 예의 표현만으로는 이유, 관점, 해결 방법을 인정하지 않는다
- 상대방에게 구체적인 행동 변화를 요구한 경우에는 `REQUEST`로 인정할 수 있다

과대평가하지 않는 표현 예시:

```
잘해줘야 해요.
도와줘야 해요.
착하게 해야 해요.
그러면 안 돼요.
```

행동 대상과 방법이 구체적으로 포함되면 장면 기준에 따라 `REQUEST` 또는 `SOLUTION`으로 인정할 수 있다.

### 6.5 발화 분석 입력 명세 (주최측)

```json
{
  "sceneContext": "현재 장면의 상황과 갈등 설명",
  "goal": "이 장면에서 아이가 생각하고 표현하도록 유도할 학습 목표",
  "previousCharacterMessage": "직전 캐릭터 발화 또는 null",
  "childUtterance": "아이의 최신 발화",
  "targetElements": ["PERSPECTIVE", "REASON", "SOLUTION"],
  "elementCriteria": {
    "PERSPECTIVE": "이 장면에서 관점 요소로 인정할 기준",
    "REASON": "이 장면에서 이유 요소로 인정할 기준",
    "SOLUTION": "이 장면에서 해결 방법으로 인정할 기준"
  }
}
```

| 필드 | 설명 |
| --- | --- |
| `sceneContext` | 현재 장면의 인물, 상황, 갈등에 대한 설명 |
| `goal` | 장면의 학습 목표 |
| `previousCharacterMessage` | 생략된 대상이나 문맥을 파악하기 위한 직전 캐릭터 발화 |
| `childUtterance` | 이번 턴에서 분석할 아이의 최신 발화 |
| `targetElements` | 해당 장면에서 주요하게 확인할 사고 요소 |
| `elementCriteria` | 해당 장면에서 각 사고 요소를 인정하기 위한 기준 |

`targetElements`는 자동으로 감지되는 정답 목록이 아니다. 실제 발화가 장면별 `elementCriteria`를 충족하고, 아이 발화 안에서 원문 근거가 확인될 때만 해당 요소를 인정한다.

> **분석 LLM 입력에 넣지 않는 값**: `story_title`, `character_name`, `accumulated_elements`, `current_child_turn_count`. 이 값들은 서버 측 모드 결정에서만 사용한다.

`sceneContext`는 `scene_description`과 `conflict`를 합쳐 구성한다. 방귀 뀌는 며느리의 `conflict` 실제 값은 7.5.1, `elementCriteria` 실제 값은 7.5.2를 참조한다.

### 6.6 발화 분석 출력 명세 (주최측)

```json
{
  "childIntent": "REASONING",
  "detectedElements": [
    {
      "type": "PERSPECTIVE",
      "evidence": "창피해서 계속 참았어요"
    }
  ],
  "utteranceValidity": "VALID"
}
```

`childIntent` 허용 값:

```
QUESTION, OPINION, REASONING, SOLUTION, DECISION, PERSPECTIVE,
EMOTION, REQUEST, CHALLENGE, PLAYFUL, OFF_TOPIC, SHORT_RESPONSE, UNCLEAR
```

`childIntent`는 주로 캐릭터의 반응 방식과 말투를 조정하는 데 사용한다. **장면 목표 달성 여부는 `childIntent`가 아니라 `detectedElements`를 기준으로 판단한다.**

`utteranceValidity` 허용 값 및 기준:

| 값 | 기준 |
| --- | --- |
| `VALID` | 의미가 파악되는 유효 발화 |
| `SHORT` | 지나치게 짧음 |
| `UNCLEAR` | 뜻을 알기 어려움 |
| `OFF_TOPIC` | 장면과 관련 없음 |
| `PLAYFUL` | 장난·소리 흉내 등 |

> 분석 LLM은 `child_intent`, `main_point`, `detected_elements`, `utterance_validity`만 제안한다.

### 6.7 서버 후처리 원칙 (주최측)

분석 모델의 출력은 바로 사용하지 않고 서버에서 검증한다.

1. `evidence`가 아이의 최신 발화에 실제로 포함되어 있는지 확인한다
2. 존재하지 않는 원문을 근거로 제시한 요소는 삭제한다
3. 같은 사고 요소가 한 턴에 중복 탐지된 경우 하나로 정리한다
4. 스키마에 정의되지 않은 요소는 제거한다
5. 구체성이 부족한 해결 방법 탐지는 필요에 따라 보정한다

> 후처리는 모델이 생성한 새로운 의미를 추가하는 과정이 아니다. 형식적으로 신뢰할 수 없는 항목을 제거하거나 정리하는 안전장치다.

### 6.8 누적 요소 계산 (주최측)

```
새 accumulatedElements = 기존 accumulatedElements ∪ detectedElements의 type
missingElements = requiredElements − 새 accumulatedElements
```

`missingElements`는 DB 컬럼으로 저장하지 않고 서버에서 계산한다.

`required_elements`는 아이가 한 번의 발화에서 모두 말해야 한다는 뜻이 아니다. 현재 장면의 여러 발화를 통해 목표 요소를 누적해서 확인한다. 대화 중 이미 충족된 요소는 유지하며, 부족한 요소만 다음 질문에 반영한다.

누적 예시:

```
1턴: EMOTION 충족
2턴: PERSPECTIVE 충족
3턴: REASON 충족
4턴: REQUEST 충족
→ 장면 목표 완료
```

### 6.9 진행 판단 규칙 (주최측)

| 조건 | 결과 |
| --- | --- |
| `turnCount >= preferred_turns` 이고 missing 없음 | `CLOSING`, `endReason = GOAL_MET` |
| missing 있고, 명백한 0정보 거절·회피·거친 말 또는 저정보 2회 연속 또는 신규 요소 없음 2회 또는 남은 턴 ≤ 2 | `GUIDED` + `guidanceTarget` |
| GUIDED 보호 횟수가 장면당 2회 미만 | 해당 GUIDED 턴은 진행·미션 턴을 소모하지 않고 `CLOSING`보다 우선 |
| `turnCount >= max_turns`이고 GUIDED 보호 없음 | `CLOSING`, `endReason = MAX_TURNS` |
| 첫 아이 발화 / 이번 턴 신규 요소 있음 | `NORMAL` 강제 (단, 위 GUIDED 보호 조건이 우선) |

보조 상태 판정 기준:

- `turns_without_new_element`: 새 사고 요소가 안 잡힌 턴이 **2번 연속**이면 유도
- `consecutive_low_information_turns`: `SHORT` / `UNCLEAR` / `OFF_TOPIC`이 **2번 연속**이면 유도

> `utterance_validity`가 `VALID`이어도 필수 요소가 남으면 `scene_goal_met`은 `false`일 수 있다.

#### 진행 모드 판단 순서 (주최측)

내부 임계값은 장면과 운영 정책에 따라 관리하되, 판단 순서는 다음을 따른다. **순서를 바꾸면 결과가 달라지므로 구현 시 이 순서를 지킨다.**

```
1. 목표 충족 종료 확인
   └─ 필수 요소 충족 및 최소 대화량 충족

2. GUIDED 필요성·보호 확인
   ├─ 필수 요소가 남아 있음
   ├─ 명백한 0정보 거절·회피·거친 말(첫 발화도 즉시 후보)
   ├─ 짧거나 불명확한 발화가 반복됨
   ├─ 여러 턴 동안 새로운 사고 요소가 확인되지 않음
   ├─ 장면 종료까지 남은 대화 기회가 적음
   └─ 장면당 GUIDED 보호 2회를 아직 쓰지 않음

3. 최대 대화 범위 확인
   └─ GUIDED 보호가 없을 때만 `MAX_TURNS` 종료

4. 일반 반응 제한 확인
   ├─ 첫 발화
   └─ 이번 턴에 새로운 요소가 확인됨

5. 위 조건에 해당하지 않으면 NORMAL
```

진행 판단의 핵심은 한 발화의 점수만 보는 것이 아니라, 누적된 사고 요소와 최근 대화 흐름을 함께 보는 것이다.

여기서 명백한 0정보 거절·회피·거친 말은 `싫어`, `몰라`, `모르겠어`, `닥쳐`, STT 오인식 `닥처`처럼
장면의 사고 요소가 전혀 확인되지 않는 한마디 발화를 말한다. 주최측의 "반복" 기준은 일반적인 짧은
발화에 적용하고, 이 경우만 팀 운영 정책으로 **첫 발화부터** GUIDED 보호 후보로 처리한다.

진행 판단에 사용하는 상태:

| 상태 | 설명 | 대응 필드 |
| --- | --- | --- |
| `turnCount` | 현재까지 아이가 발화한 횟수 | `current_child_turn_count` |
| `newlyDetected` | 이번 턴에서 새롭게 확인된 사고 요소 | `last_detected_elements` |
| `accumulatedElements` | 장면 시작 이후 누적된 사고 요소 | `accumulated_elements` |
| `missingElements` | 필수 요소 중 아직 확인되지 않은 요소 | 서버 계산 |
| `turnsWithoutProgress` | 새로운 요소가 확인되지 않은 대화의 연속 횟수 | `turns_without_new_element` |
| `lowInformationTurns` | 짧거나 불명확한 발화가 이어진 횟수 | `consecutive_low_information_turns` |
| `guidedTurnProtectionUsed` | 현재 장면에서 소모한 GUIDED 보호 횟수(최대 2) | `guided_turn_protection_used` |
| `previousMode` | 직전 턴의 진행 모드 | `last_response_mode` |
| `previousGuidanceTarget` | 직전에 유도한 사고 요소 | `last_guidance_target` |

> 누적 요소는 모델이 한 번 탐지한 모든 요소가 아니라, 장면 기준과 서버 검증을 통과한 요소를 대상으로 한다.

#### 유도 대상 선택 원칙 (주최측)

`GUIDED` 모드가 선택되면 아직 충족되지 않은 필수 요소 중 하나를 유도 대상으로 정한다.

- 아직 충족되지 않은 필수 요소를 우선한다
- 직전에 유도한 요소와 동일한 요소가 반복되지 않도록 한다
- 장면에서 설정한 기본 우선순위를 참고할 수 있다
- 아이가 방금 말한 내용과 가장 자연스럽게 연결되는 요소를 우선할 수 있다

### 6.10 응답 모드 (주최측)

| 모드 | 처리 |
| --- | --- |
| `NORMAL` | 일반 반응. 캐릭터 모델 호출 |
| `GUIDED` | 부족한 요소로 유도. 캐릭터 모델 호출 + `guidanceTarget` 및 캐릭터 걱정 정보 전달. 장면당 처음 2회는 진행·미션 턴 보호 |
| `CLOSING` | 장면 종료. 고정 마지막 대사(`character_closing`)를 조회해 `messages`에 저장하고 재생 |

> **`CLOSING`이 결정되면 LLM이 마지막 대사를 생성하지 않는다.**

최대 턴 도달 시 처리:

```
최대 턴 도달
→ 현재까지 아이가 말한 내용에 짧게 반응
→ 캐릭터 마지막 대사
→ 다음 전개 이동
```

목표를 모두 충족하지 못했더라도 최대 턴에 도달하면 장면을 종료한다. 단, 마지막 응답은 평가나 지적이 아니라 자연스럽게 다음 이야기로 연결되어야 한다.

### 6.11 장면별 설정 데이터 구조 (주최측)

```json
{
  "sceneId": "scene_example",
  "goal": "장면 학습 목표",
  "requiredElements": ["PERSPECTIVE", "REASON", "SOLUTION"],
  "elementCriteria": {
    "PERSPECTIVE": "장면별 인정 기준",
    "REASON": "장면별 인정 기준",
    "SOLUTION": "장면별 인정 기준"
  },
  "character": {
    "remainingWorries": {
      "PERSPECTIVE": "캐릭터가 아직 해소하지 못한 관점 관련 걱정",
      "REASON": "캐릭터가 아직 해소하지 못한 이유 관련 걱정",
      "SOLUTION": "캐릭터가 아직 해소하지 못한 방법 관련 걱정"
    }
  }
}
```

`goal`, `requiredElements`, `elementCriteria`는 장면의 학습·분석 기준이다. `remainingWorries`는 캐릭터에 속하며 유도 시 캐릭터 모델에 전달된다.

같은 `REASON` 요소라도 장면에 따라 인정 기준은 달라질 수 있다. 따라서 사고 요소의 이름만으로 목표 달성을 판단하지 않고, 장면별 기준을 함께 적용해야 한다.

### 6.12 캐릭터 응답 모듈 입력 (주최측)

- 아이의 최신 발화
- 발화 분석 결과
- 현재 진행 모드
- 캐릭터의 감정과 상황
- 필요한 경우 유도에 사용할 캐릭터의 걱정 정보

### 6.13 발화 성격에 따른 반응 원칙 키 (주최측)

| 조건 | `reactionKey` | 동작 |
| --- | --- | --- |
| PLAYFUL / OFF_TOPIC / validity PLAYFUL | `playfulUtterance` | 장난을 실제 사건으로 단정하지 않고 받아침 |
| QUESTION | `questionFromChild` | 질문에 먼저 답함 |
| SOLUTION intent 또는 detected | `proposalFromChild` | 제안의 도움 되는 점 인정, 중간 턴에서는 걱정 하나만 |
| SHORT / UNCLEAR 등 | `unclearUtterance` | 첫 반응은 비판하지 않고 짧게 수용. GUIDED에서는 캐릭터의 구체적 걱정과 장면 질문 하나로 대화를 다시 이음 |
| EMPATHY detected 등 | `empathyFromChild` / `directResponse` | 공감 반응 |
| 의견·반박·결정 등 | `disagreement` | 무조건 부정하지 않고 걱정 하나 |
| CLOSING | `directResponse` | 마무리 톤 (중간 턴 "장면 닫지 말 것"과 충돌 방지) |
| 그 외 | `directResponse` | 최신 말에 직접 반응 |

> `CLOSING` 턴에서는 의도 매핑을 무시하고 `directResponse`를 사용한다.

`childIntent`별 매핑 (주최측):

| 코드 | 쓰임 |
| --- | --- |
| `QUESTION` | `questionFromChild` |
| `SOLUTION` | `proposalFromChild` (SHORT보다 우선) |
| `PLAYFUL` / `OFF_TOPIC` | `playfulUtterance` |
| `UNCLEAR` / `SHORT_RESPONSE` | `unclearUtterance` |
| `EMOTION` 등 | `empathy` / `disagreement` / `direct` 등으로 매핑 |
| `OPINION`, `REASONING`, `DECISION`, `PERSPECTIVE`, `REQUEST`, `CHALLENGE` | `disagreement` 등 |

`utteranceValidity`별 서버 영향 (주최측):

| 값 | 서버 영향 |
| --- | --- |
| `VALID` | 일반 경로 |
| `SHORT` | 저정보 카운트 / unclear 반응 후보 |
| `UNCLEAR` | 저정보 카운트 / unclear 반응 |
| `OFF_TOPIC` | 저정보 카운트 / playful 반응 쪽 |
| `PLAYFUL` | soft-cue 스킵 / playful 반응 |

### 6.14 사고 요소 보완 — GUIDED와 soft-cue (주최측)

| 경로 | 조건 | 재료 |
| --- | --- | --- |
| GUIDED 모드 | 규칙상 GUIDED + `guidanceTarget` | `remainingWorries[guidanceTarget]` → mode instruction의 focus |
| NORMAL soft-cue | NORMAL + 신규 요소 + missing 남음 + soft 허용 반응 | `remainingWorries[softTarget]` → `softRemainingWorry` |
| 재료 없음 | 해당 키에 worry 없음 | **교육용 fallback 문구를 넣지 않음** |

**soft-cue 규칙**: 모드가 `NORMAL`이어도, 신규 요소가 잡혔고 missing이 남아 있으며 장난·질문·불명확 반응이 아니면 `remainingWorries[대상요소]`를 약한 유도로 넣을 수 있다. 이때 `responseMode`는 여전히 `NORMAL`일 수 있다.

**soft-cue 스킵 대상**: `playfulUtterance`, `questionFromChild`, `unclearUtterance`

`guidanceStyle`은 "어떻게 드러낼지"의 캐릭터별 표현 방식이다. 방귀 뀌는 며느리의 `remainingWorries`와 `guidanceStyle` 실제 값은 7.5.3을 참조한다.

> **구현 경계** (주최측): 분석 LLM은 아이 발화의 의도·요소·유효성을 구조화하고, 서버 규칙은 진행 모드와 종료 여부를 확정하며, 캐릭터 LLM은 주어진 모드와 반응 원칙에 따라 대사만 생성한다.

### 6.15 캐릭터 유도 방식 (주최측)

진행 엔진은 아이에게 직접 질문할 문장을 생성하지 않는다. 부족한 사고 요소의 이름을 선택하고, 장면에 등록된 캐릭터의 `remainingWorries` 정보를 캐릭터 모델에 전달한다.

```
부족한 요소: SOLUTION
        │
        ▼
remainingWorries.SOLUTION
        │
        ▼
캐릭터가 아직 걱정하는 내용으로 표현
```

부족한 요소가 `SOLUTION`인 경우에도 다음처럼 직접적인 학습 질문을 사용하지 않는 것을 원칙으로 한다.

```
해결 방법을 말해 봐.
다른 방법은 무엇이 있을까?
```

대신 캐릭터의 상황과 감정 안에서 걱정을 드러낸다.

```
그런데 다음에도 같은 일이 생기면 어떡하지?
```

이 구조를 통해 유도 질문이 학습지 문항처럼 보이지 않고 이야기 속 대화로 이어지도록 한다.

`SHORT`·`UNCLEAR`·`OFF_TOPIC`이 반복되어 GUIDED가 된 경우에는, 캐릭터의 구체적 걱정을 먼저
드러낸 뒤 **장면에 답할 수 있는 질문 하나**를 덧붙일 수 있다. 이 질문은 아이를 꾸짖거나 답을
채점하지 않고, 다시 이야기 안으로 참여시키는 용도다.

```
하기 싫을 수도 있지, 나는 배를 안전하게 딸 길이 걱정되는데 넌 어때?
```

강한 유도(`GUIDED`) 시 추가 원칙:

- 한 번에 하나의 사고 요소만 유도한다
- 직전 유도와 같은 형태를 반복하지 않는다
- 정답이나 모범 답안을 캐릭터가 먼저 말하지 않는다

### 6.16 처리 결과 예시 (주최측)

장면의 필수 사고 요소가 `PERSPECTIVE`, `REASON`, `SOLUTION`인 경우다.

**첫 번째 발화**

```
아이: 며느리가 창피해서 계속 참았던 것 같아요.
```

분석 결과:

```json
{
  "childIntent": "PERSPECTIVE",
  "detectedElements": [
    { "type": "PERSPECTIVE", "evidence": "창피해서 계속 참았던 것 같아요" }
  ],
  "utteranceValidity": "VALID"
}
```

진행 결과:

```json
{
  "mode": "NORMAL",
  "accumulatedElements": ["PERSPECTIVE"],
  "missingElements": ["REASON", "SOLUTION"]
}
```

캐릭터는 아이가 말한 며느리의 사정을 받아주고, 필요하면 남은 걱정을 약하게 드러낼 수 있다.

**짧은 발화가 반복되는 경우**

```
아이: 네.
아이: 음….
```

새로운 사고 요소가 확인되지 않고 저정보 발화가 누적된다. 필수 요소가 남아 있고 대화가 정체되었다고 판단하면 다음과 같이 처리한다.

```json
{
  "mode": "GUIDED",
  "guidanceTarget": "REASON"
}
```

캐릭터 모델에는 `REASON`에 대응하는 캐릭터의 남은 걱정을 전달한다.

**필수 요소가 충족된 경우**

```json
{
  "mode": "CLOSING",
  "closingReason": "GOAL_MET"
}
```

**최대 대화 범위에 도달한 경우**

```json
{
  "mode": "CLOSING",
  "closingReason": "MAX_TURNS"
}
```

#### 7.5.1 conflict (팀 작성)

`story_scenes`의 `conflict`는 필수 컬럼이며, 발화 분석 입력의 `sceneContext`는 `scene_description`과 `conflict`를 합쳐 구성하도록 정의되어 있다. 그러나 제공된 장면 구성 테이블에 `conflict` 값이 포함되어 있지 않아 팀이 작성한다.

**작성 원칙**:

- 상황 서술이 아니라 **캐릭터 시점의 딜레마**로 쓴다. `scene_description`이 "무슨 일이 일어났는가"라면 `conflict`는 "이 캐릭터가 무엇 때문에 막혀 있는가"다
- 한 문장으로 쓴다. 분석 입력에 길이 제한이 명시되어 있다
- "A하면 B가 걱정된다" 구조로 양쪽 축을 담는다
- 아이가 찾아야 할 해결책을 암시하지 않는다

| 장면 | `conflict` |
| --- | --- |
| 대화1 (`sc_banggui_03`) | 참으면 몸이 점점 힘들어지지만, 사실을 말하면 가족들이 자신을 이상하게 볼까 봐 말하지 못하고 있다. |
| 대화2 (`sc_banggui_05`) | 며느리의 방귀에 크게 놀라 집안 체면을 걱정하면서도, 며느리를 정말 내보내야 하는지 마음을 정하지 못하고 있다. |
| 대화3 (`sc_banggui_07`) | 배를 따고 싶지만 장대도 닿지 않고 나무에 오를 수도 없어 방법을 찾지 못하고 있다. |

| --- | --- |
| `EMOTION` | 며느리 또는 아이 자신의 감정을 직접 가리키는 말을 한 경우 |
| `PERSPECTIVE` | 며느리 또는 다른 사람의 특징을 그 사람 입장에서 바라보고 말한 경우 |
| `RESULT` | 그 특징을 좋은 일에 썼을 때 생기는 일을 말한 경우 |
| `SOLUTION` | 특징을 숨기지 않고 쓰기 위한 구체적 방법을 말한 경우. 미리 알려주기, 필요한 때만 쓰기 등 |

#### 7.5.3 remainingWorries와 guidanceStyle (팀 작성)

`remainingWorries`는 GUIDED 모드와 NORMAL soft-cue에서 캐릭터 응답 모듈에 전달하는 유도 재료다. 주최측 문서에 "`remainingWorries`는 캐릭터에 속하며 유도 시 캐릭터 모델에 전달된다", "재료가 없으면 교육용 fallback 문구를 넣지 않는다"고 규정되어 있다. 제공 자료에 실제 값이 없어 팀이 작성한다.

**작성 원칙**:

- 캐릭터 1인칭, 캐릭터 말투로 쓴다. 그대로 대사가 되지는 않으나 톤이 전달된다
- **질문이 아니라 걱정으로 쓴다.** 질문 형태로 쓰면 모델이 그대로 복사해 매 턴 같은 질문을 반복한다
- 부족한 요소를 아이가 채우고 싶게 만든다. `REASON`이 부족하면 "왜 그런지 모르겠어"가 자연스럽게 이유를 유도한다
- 요소별로 반드시 다르게 쓴다. 하나를 여러 요소에 재사용하면 유도 대상이 뭉개진다

**대화1 — 며느리** · `guidanceStyle`: 조심스럽고 걱정이 많은 말투

| 요소 | `remainingWorry` |
| --- | --- |
| `PERSPECTIVE` | 가족들이 내 사정을 알아줄지 도무지 모르겠어. |
| `EMOTION` | 내가 얼마나 힘든지 아무도 몰라주는 것 같아. |
| `REASON` | 왜 꼭 말해야 하는지 나는 아직 잘 모르겠어. |
| `SOLUTION` | 말을 꺼내고 싶어도 어떻게 시작해야 할지 모르겠어. |

**대화2 — 시아버지** · `guidanceStyle`: 완고하고 언성이 높은 말투

| 요소 | `remainingWorry` |
| --- | --- |
| `PERSPECTIVE` | 며느리에게 무슨 사정이 있었는지 나는 알 길이 없구나. |
| `EMOTION` | 나는 아직도 놀란 가슴이 가라앉지 않는구나. |
| `REASON` | 일부러 그런 것이 아니라는 걸 내가 어찌 믿겠느냐. |
| `SOLUTION` | 그래서 나더러 어찌하란 말이냐. |

**대화3 — 마을 이장** · `guidanceStyle`: 사람 좋고 답답해하는 말투

| 요소 | `remainingWorry` |
| --- | --- |
| `SOLUTION` | 배를 딸 방도가 도무지 떠오르지 않는구려. |
| `REASON` | 그 방법이 정말 통할지 나는 알 수가 없구려. |
| `REQUEST` | 며느리에게 어찌 부탁을 해야 할지 모르겠구려. |
| `RESULT` | 사람들이 다치지나 않을까 그것이 걱정이구려. |

**대화4 — 며느리** · `guidanceStyle`: 조금 밝아졌으나 아직 조심스러운 말투

| 요소 | `remainingWorry` |
| --- | --- |
| `EMOTION` | 아직은 마음이 조금 어색해. |
| `PERSPECTIVE` | 다른 사람들도 나처럼 남과 다른 점이 있을까. |
| `RESULT` | 내가 방귀를 뀌면 또 무슨 일이 생길지 모르겠어. |
| `SOLUTION` | 언제 어떻게 써야 좋을지 아직 모르겠어. |

> 며느리는 대화1과 대화4에 모두 등장하지만 심리 상태가 다르므로 값을 별도로 둔다.
> 따라서 `remainingWorries`와 `guidanceStyle`은 캐릭터 단위가 아니라 **캐릭터와 장면의 조합 단위**로 관리한다.
> 캐릭터 성격 원문: [../reference/characters.md](../reference/characters.md)

#### 7.5.4 팀 작성 값에 대한 유의사항

`conflict`, `elementCriteria`, `remainingWorries`, `guidanceStyle`은 자문위원 검수를 거친 고정 대사와 달리 **팀 창작물**이다.

- `elementCriteria`가 느슨하면 목표가 쉽게 충족되어 장면이 빠르게 종료되고, 지나치게 엄격하면 아이가 `max_turns`까지 유도만 받게 된다
- 실제 발화 샘플로 검증한 뒤 조정하는 것을 전제로 한다
- 주최측에 팀이 작성한 값임을 공유하고, 확정 시 이슈 로그 I-15~17을 갱신한다

### 7.6 미션 (주최측)

#### 미션 노출 원칙

미션은 대화 시작과 동시에 보여주지 않는다. 아이의 발화 흐름을 확인한 뒤, 해결 방법을 실제로 구성해야 하는 시점에 노출한다.

```
캐릭터 첫 대사
→ 아이가 자유롭게 해결 방법 제안
→ 해결 방향이 나타나는지 확인
→ 구체적인 실행이 필요한 시점 판단
→ 미션 노출
→ 아이가 미션 수행
→ 미션 결과를 다음 대화에 반영
```

#### 미션1 노출 조건 (다음 중 하나에 해당할 때)

- 아이가 며느리의 방귀를 활용할 수 있다고 제안한 경우
- 아이가 해결 방향은 말했지만 방법이 구체적이지 않은 경우
- 2회 이상 대화했지만 실행 방법이 나오지 않은 경우
- 캐릭터 질문만으로 해결 방법을 구체화하기 어려운 경우

#### 미션1 — 높이 있는 배 따기

**목적**: 높은 배나무의 배를 떨어뜨리기 위해 며느리의 큰 방귀를 안전하게 사용하는 방법을 구성한다.

확인 항목:

- 무엇을 사용할 것인지
- 그 방법이 왜 가능한지 (D-54 — 원래 "주변 사람들이 어디로 피해야 할지"였으나 첫 항목과
  같은 SOLUTION으로 겹쳐 체크리스트가 채워지지 않는 문제가 있어, 장면7에 이미 있는 REASON
  요소에 맞춰 정정. [backend/docs/decisions.md D-54](../../backend/docs/decisions.md))
- 며느리에게 어떻게 부탁할 것인지
- 그 결과 어떤 일이 생길지

미션 결과는 단순 정답 여부가 아니라 위 요소 확인에 활용한다.

#### 미션2 — 친구들의 단점을 장점으로 바꾸기

**목적**: 친구나 주변 사람의 특징을 다른 관점에서 바라보고, 단점처럼 보이는 특징을 장점이나 가능성으로 바꾸어 말한다.

노출 시점:

```
아이가 며느리에게 자신의 특징을 부끄러워하지 않아도 된다고 말함
→ 자신의 특징을 긍정하는 이유 확인
→ 다른 사람의 특징으로 관점을 확장할 필요가 생김
→ 미션2 노출
```

처음부터 미션을 보여주면 아이가 정해진 답을 찾으려 할 수 있으므로, 며느리의 질문에 먼저 자신의 생각을 말한 뒤 노출한다.

예시:

- 목소리가 큰 친구는 멀리 있는 사람을 부를 수 있어요.
- 질문이 많은 친구는 새로운 생각을 찾을 수 있어요.
- 힘이 센 친구는 무거운 물건을 옮길 때 도울 수 있어요.
- 조용한 친구는 다른 사람의 말을 잘 들어 줄 수 있어요.

#### 미션 데이터 처리 방침 (팀 결정)

**미션은 별도 테이블에 저장하지 않는다.**

- 미션 정의(목적, 안내 문구, 예시)는 코드 상수로 관리한다
- 미션 수행 중 아이의 발화는 `messages`에 저장되고, 그 분석 결과는 `utterance_analyses`에 저장되므로 미션 성과는 기존 테이블에 이미 기록된다
- 미션 노출 시점에 `messages`에 `speaker_type = system` 메시지를 1건 저장한다. 다음 턴에서 해당 `scene_id`에 system 메시지가 존재하는지 조회해 중복 노출을 방지한다

**결정 근거**: 주최측이 제공한 9개 테이블 어디에도 미션 관련 컬럼이 없으며, 미션 결과를 사고 요소 확인에 활용한다고 명시되어 있다. `speaker_type`의 `system` 값은 테이블 정의서에 이미 정의되어 있어 스키마 변경 없이 구현 가능하다.

### 7.7 character_closing 출력 조건 (주최측)

다음 중 하나일 때 `character_closing`을 출력한다.

1. 필수 목표 요소가 모두 충족된 경우
2. `max_turns`에 도달한 경우
3. 미션 필수 장면에서 미션과 핵심 발화가 완료된 경우

### 7.8 말하기 후 활동 설정 (팀 결정)

주최측은 카드 이미지로 전개 이미지 위주 사용을 권장했으며, 핵심 단어는 아이 발화에서 인식되는지가 중요하므로 자유 구성이 가능하다고 답변했다. 카드 이미지는 주최측이 제공하는 동화 이미지에 포함된다.

#### 원문 간 차이와 팀 결정

주최측 답변에 따르면 말하기 후 활동의 실제 진행은 다음과 같다.

> 대표 장면 4가지를 활용해 각 장면에 핵심 키워드를 3~4개 제공하고, 우선 이미지를 이야기 순서에 맞게 선택한다. 순서가 맞으면 이미지와 단어를 참고해 아이가 이야기를 자신의 언어로 말한다.

이는 MVP 요건 문서의 기술과 두 가지가 다르다.

| 항목 | MVP 요건 | 주최측 Q&A 답변 | 팀 결정 |
| --- | --- | --- | --- |
| 카드 형식 | 장면 카드 4~5개 | 대표 장면 이미지 4개 | 이미지 카드로 구성하되 접근성을 위해 텍스트를 병기 |
| 핵심 단어 수 | 3~4개 | 각 장면에 3~4개 (총 12~16개) | MVP 요건 기준으로 전체 4개 사용 |

핵심 단어를 장면당 3~4개로 두면 7세~초2 아이에게 제시할 단어가 12개를 넘어 인지 부담이 크고, 인터뷰에서 지적된 "한 화면에 정보가 많지 않도록" 요구와 충돌한다. 따라서 MVP 요건 기준을 채택하되 주최측 확인을 권장한다 (I-18).

#### post_activity_config

```json
{
  "cards": [
    { "id": "card_1", "text": "며느리는 방귀를 꾹 참고 또 참았어요.", "correct_order": 1 },
    { "id": "card_2", "text": "며느리의 큰 방귀에 시아버지의 갓이 날아갔어요.", "correct_order": 2 },
    { "id": "card_3", "text": "며느리의 방귀로 높은 배나무의 배가 우수수 떨어졌어요.", "correct_order": 3 },
    { "id": "card_4", "text": "시아버지가 며느리에게 미안하다고 말했어요.", "correct_order": 4 }
  ],
  "retelling_keywords": ["며느리", "방귀", "배나무", "시아버지"]
}
```

카드는 전개1~4에 각각 대응하며, 각 카드는 해당 전개의 이미지와 함께 표시한다. 카드 텍스트는 대상 연령을 고려해 짧은 문장으로 구성하고, 키워드는 아이 발화에서 인식 가능성이 높은 명사를 선정했다.

#### 활동 완료 후 흐름 (주최측)

활동이 완료되면 이야기 세션이 종료된다. 보호자 리포트를 구현하는 경우 리포트 화면으로 이동한다. 본 MVP는 리포트를 선택 항목으로 두므로 기본 흐름은 세션 종료다.

`created_at` 세 컬럼뿐이었으나, 카카오 로그인으로 재방문한 사용자를 조회할 방법이 없었다.
`provider_id`로 재방문 사용자를 식별한다 (unique). `email`은 **nullable**이다 — 카카오 이메일
동의항목이 선택 동의로 빠질 수 있고, 식별은 `provider_id`로 하므로 이메일 없이도 서비스가
완전히 동작한다 ([backend/docs/decisions.md](../../backend/docs/decisions.md) D-18).

**`situation`·`child_role` 추가 근거** (팀 결정, 2026-08-12): 4.1 F-03에 두 문구가 확정값으로
정의되어 있으나 저장할 컬럼이 없었다. 화면 명세는 "이야기 상황 = 첫 장면 `conflict`"라고 기술했으나,
`conflict`는 장면별 캐릭터 딜레마이며 발화 분석 입력(`sceneContext`)에 쓰이는 값이므로 성격이 다르다
(7.5.1 참조). **`conflict`를 화면에 사용하지 않는다.** 코드 상수 대신 컬럼으로 둔 이유는
`story_id` 분기 코드를 없애기 위함이다.

**`cover_image_url` 추가 근거** (팀 결정, 2026-08-12): API 계약이 `coverImageUrl`을 내려주도록
정의되어 있으나 대응 컬럼이 없었다. **서버는 이미지 바이트를 서빙하지 않고 URL 문자열만 응답한다.**
서빙하면 아이가 화면을 넘길 때마다 슬립 상태의 배포 서버를 깨우는 요청이 이미지 개수만큼 발생한다.
URL의 실제 형태(오브젝트 스토리지 절대 URL vs 프론트 정적 상대경로)는 에셋 수령 시 확정한다.

- `status` 값: `draft`, `published`, `archived`
- 카드 내용과 정답 순서는 별도 카드 테이블 없이 `post_activity_config`에 저장한다
- 후속 활동 카드 이미지는 `post_activity_config` 안에 `imageUrl`로 함께 둔다. 스키마 변경이 없다
- `story_versions` 테이블은 MVP에서 만들지 않는다
- 이미 세션에서 사용된 이야기를 수정해야 하면 기존 내용을 직접 변경하지 않고, 이야기와 장면을 복사해 새로운 `story_id`로 등록한다

| `scene_goal` | `text` | 조건부 | 장면에서 이끌어내고자 하는 발화 목표 |
| `required_elements` | `text[]` | 조건부 | 장면 목표 충족에 필요한 사고 요소 |

| `preferred_turns` | `smallint` | 조건부 | 목표 충족 종료를 위한 최소 아이 발화 횟수 |
| `max_turns` | `smallint` | 조건부 | 장면에서 허용하는 최대 아이 발화 횟수 |

`scene_type` 값 (팀 결정):

| 값 | 설명 | 대상 장면 |
| --- | --- | --- |
| `intro` | 도입. 전체 화면 스토리, 아이 발화 없음 | `sc_banggui_01` |
| `narrative` | 전개. 스토리 표시, 아이 발화 없음 | `sc_banggui_02`, `04`, `06`, `08` |
| `dialogue` | 대화. 캐릭터와 아이의 1:1 음성 대화 | `sc_banggui_03`, `05`, `07`, `09` |

**조건부 필수 규칙** (팀 결정): 주최측 정의서는 위 컬럼을 모두 필수(Y)로 두었으나, 제공된 장면 구성 테이블에서 도입·전개 장면은 해당 값이 존재하지 않는다. 따라서 `scene_type = dialogue`인 경우에만 필수로 하고, `intro` / `narrative`인 경우 nullable로 완화한다.

**`element_criteria` 컬럼 추가 근거** (팀 결정): 발화 분석 입력의 필수 항목이나 주최측 테이블 정의서에 대응 컬럼이 없다. 장면별 학습 기준이며 테스트 과정에서 반복 조정될 값이므로, 코드 배포 없이 수정할 수 있도록 DB에 둔다. 저장 형식은 7.5.2의 요소별 기준을 요소명을 키로 하는 jsonb로 저장한다.

```json
{
  "PERSPECTIVE": "며느리가 처한 상황이나 가족이 받아들일 방식을 며느리·가족 중 한쪽의 입장에서 헤아려 말한 경우",
  "EMOTION": "며느리 또는 아이 자신의 감정을 직접 가리키는 말을 한 경우. 감정어가 발화에 실제로 나타나야 함"
}
```

**`remainingWorries`와 `guidanceStyle`의 저장 위치** (팀 결정): 이 두 값은 분석 기준이 아니라 캐릭터 응답 모듈에 전달하는 대사 재료이므로 `story_scenes`에 두지 않고 **코드 상수 또는 캐릭터 설정**으로 관리한다. 며느리가 대화1과 대화4에 모두 등장하나 심리 상태가 달라 값이 다르므로, 캐릭터 단위가 아니라 캐릭터와 장면의 조합을 키로 사용한다.

장면 진행 순서 (주최측):

```
character_opening
→ 아이와 캐릭터 대화
→ 목표 충족 또는 최대 발화 횟수 도달
→ character_closing 재생
→ 다음 장면 이동
```

### 8.10 utterance_analyses (주최측)

| 컬럼명 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | `uuid` | Y | 분석 결과 고유번호 |
| `message_id` | `uuid` | Y | 분석 대상 아이 메시지 ID |
| `child_intent` | `varchar` | Y | 이번 발화의 중심 의도 |
| `main_point` | `text` | 선택 | 아이 말의 핵심 뜻 |
| `detected_elements` | `jsonb` | Y | 이번 발화에서 확인된 사고 요소와 근거 |
| `utterance_validity` | `varchar` | Y | 이번 발화의 유효성 |

`detected_elements` 형식:

```json
[
  { "type": "REASON", "evidence": "억울하니까" },
  { "type": "PERSPECTIVE", "evidence": "토끼가 모르고 따라가면" }
]
```

- 아이 메시지만 분석한다
- 하나의 아이 메시지에는 분석 결과 한 건만 저장한다
- STT 실패는 확정된 아이 메시지가 아니므로 발화 분석 대상이 아니다
- 이번 최신 아이 발화 한 건에서 확인된 요소만 저장한다
- 현재 장면 전체의 누적 요소는 `story_sessions.accumulated_elements`에 type만 합쳐 저장한다
- `missing_elements`는 DB 컬럼으로 저장하지 않고 서버에서 계산한다
- 분석 버전은 별도 테이블 없이 `analysis_version`에 `mvp_v1` 같은 문자열만 저장해도 충분하다 (주최측 안내)

운영 데이터를 보존해야 할 때 값을 하는 도구인데, 백엔드 1인 + 시연용 데이터라 그 이점이 없다.

## 10. 제약사항 및 준수사항

### 10.1 콘텐츠 준수사항 (주최측)

- 이야기는 제공된 내용 안에서 진행한다
- 자문위원 난이도 검수가 완료되었으므로 `scene_description`, 첫 대사, 마무리 대사는 그대로 사용한다
- 내용이나 대사 수정이 필요하면 주최측과 논의 후 자문위원 재검수를 거쳐 진행한다
- 화면 구성은 기존 안에서 벗어나 자유롭게 제안할 수 있다. 아이들이 몰입해서 대화에 참여하면서도 흥미를 가질 수 있는 방향을 지향한다
- 이야기 상황과 아이 역할 문구는 팀에서 변경 가능하다
- 말하기 후 활동의 카드 이미지는 제공 자료에 포함된 이미지이며, 전개 이미지 위주 사용을 권장하나 다른 이미지 선택도 가능하다
- 핵심 단어는 아이의 발화에서 인식되는지가 중요하므로 자유롭게 구성 가능하다

### 10.2 개발 자율 범위 (주최측)

- 개발 방식은 참가자 의견을 자유롭게 반영해 가장 효율적인 방법으로 진행한다
- Supabase 외 다른 인증 방법을 사용해도 된다
- 제공된 DB는 변경해도 된다
- 아이들의 정보는 가이드를 준수하되, 그 외 데이터 처리는 임의로 가능하다
- 성능에 도움이 되는 프로그램 및 기능 제안은 환영한다

### 10.3 데이터 처리 제약 (주최측)

- **원본 음성 파일은 저장하지 않는다**
- 개인정보는 최소한만 수집한다
- 동의가 없거나 철회된 아이는 새로운 이야기 세션을 시작할 수 없다

### 10.4 비용 제약 (주최측)

- 유료 API 사용은 가능하나 현재 턴당 사용량·비용 수준을 넘기지 않는다
- 현재 기준: 분석·캐릭터 발화 모두 `gpt-5-mini` 사용, 캐릭터 대화 1세션 8턴 기준 약 **1.5만~2만 토큰**
- 토큰 소모는 줄이는 방향을 우선한다

### 10.5 알려진 제약 (주최측)

- 테스트용 음성 파일은 제공되지 않는다
- OT 발표 자료는 내부 정보 포함으로 제공되지 않는다
- 보호자 리포트의 가정 학습 가이드는 상세 기준이 없어 예시 데이터로 구성한다

```
M-58 (스키마)
   └─ M-13~M-19 (콘텐츠 데이터 적재)
          └─ M-35~M-46 (대화 엔진)
                 └─ M-47~M-50 (미션)

   └─ M-03~M-05 (계정·아이·동의)
          └─ M-08 (이어하기), 세션 생성

M-29 (STT 방식 확정)
   └─ M-33 (messages 저장 형태)
   └─ 백엔드 오디오 업로드 API 필요 여부 결정
```

M-29는 9.3절의 STT 방식이 확정되어야 착수 가능하다. Web Speech API를 선택하면 백엔드는 텍스트만 수신하고, OpenAI Whisper를 선택하면 오디오 업로드 엔드포인트가 추가로 필요하다. 프론트와 백엔드 양쪽 작업 범위가 달라지므로 **가장 먼저 결정해야 한다.**

| I-14 | 고정 대사 표기 차이 | 대화3 첫 대사가 장면 구성 테이블은 "아무도 딸 수가 없었소", 화면 흐름 문서는 "아무도 딸 수가 없었단다". 대화2 첫 대사와 대화4 마지막 대사도 띄어쓰기·문장부호 차이 존재 | 장면 구성 테이블 표기를 정본으로 사용. 화면 흐름 문서는 요약본으로 간주 |
| I-15 | `conflict` 값 미제공 | `story_scenes`의 필수 컬럼이자 발화 분석 `sceneContext` 구성 요소이나, 장면 구성 테이블에 값이 없음 | 팀이 대화 장면 4개의 값을 작성 (7.5.1 참조). **주최측 확인 권장** |
| I-16 | `elementCriteria` 값 미제공 | 발화 분석 입력의 필수 항목이며 "사고 요소 이름만으로 판단하지 말고 장면별 기준을 함께 적용"하도록 명시되어 있으나, 방귀 뀌는 며느리 4개 대화 장면의 실제 기준값이 제공되지 않음. 대응 DB 컬럼도 없음 | 팀이 장면별 요소별 기준을 작성 (7.5.2 참조). `story_scenes`에 `element_criteria` jsonb 컬럼 추가. **주최측 확인 권장** |
| I-17 | `remainingWorries`·`guidanceStyle` 값 미제공 | GUIDED·soft-cue 유도의 재료이며 값이 없으면 "교육용 fallback 문구를 넣지 않는다"고 규정되어 있으나, 장면별 실제 값이 제공되지 않음 | 팀이 캐릭터·장면 조합별로 작성 (7.5.3 참조). 코드 상수로 관리. **주최측 확인 권장** |
| I-18 | 말하기 후 활동 카드·키워드 구성 | MVP 요건은 "카드 4~5개, 핵심 단어 3~4개", 주최측 Q&A 답변은 "대표 장면 이미지 4개, 각 장면에 키워드 3~4개(총 12~16개)" | MVP 요건 기준 채택. 카드 4개(이미지+텍스트 병기), 키워드 전체 4개. 인지 부담과 인터뷰 요구를 근거로 함. **주최측 확인 권장** |
| I-19 | 카드 이미지 제공 여부 | 주최측이 "말하기 후 활동 카드 이미지는 제공 자료에 포함되는 이미지"라고 답변 | 전개 이미지를 카드 이미지로 사용. 이미지 파일 수령 전까지 플레이스홀더로 진행 |
| I-20 | GUIDED 보호 횟수 상태 | 제공 테이블에는 반복 저정보 발화에서 GUIDED 기회를 보존할 상태가 없음 | 팀이 `guided_turn_protection_used`를 세션 상태에 추가. 장면당 2회만 진행·미션 턴을 보호하고, 보호 소진 뒤에는 기존 종료 규칙을 적용 |

### 13.1 주최측 확인 권장 사항

다음 항목은 팀이 결정했으나 주최측 확인을 받는 편이 안전하다.

| 항목 | 이유 |
| --- | --- |
| 전개2 정본 선택 (I-04) | `scene_description`은 자문위원 검수 완료 텍스트로 수정 불가 원칙이 있으나, 팀이 전체 줄거리 버전을 선택함 |
| `conflict` / `elementCriteria` / `remainingWorries` / `guidanceStyle` (7.5.1~7.5.3) | 대화 엔진 동작에 직접 영향을 주는 팀 창작물이며, 검수된 난이도와 어긋날 수 있음 |
| `post_activity_config` 카드 문구 (I-08) | 주최측이 자유 구성을 허용했으나, 아동 대상 문장이므로 난이도 확인이 필요할 수 있음 |
| 말하기 후 활동 키워드 개수 (I-18) | MVP 요건(3~4개)과 Q&A 답변(장면당 3~4개)이 달라 팀이 전자를 채택함 |
