## 0. 먼저 — 요구 6·8이 지목한 "답답함"의 공통 원인

요구 6("자막 width를 2배로")과 요구 8("대사 width를 늘려줘")은 취향 문제가 아니라
**단위를 잘못 쓴 버그**입니다. 브라우저에서 직접 재봤습니다.

### 측정값 (Pretendard, 1280×800, 루트 16px)

| 글자 크기 | `1ch` (숫자 0의 폭) | 한글 1자 | 비율 |
| --- | --- | --- | --- |
| 32px (`text-narration`) | 19.75px | 27.66px | **1.40** |
| 31px (`text-dialogue`) | 19.13px | 26.79px | **1.40** |
| 21px (`text-kid-body`) | 12.96px | 18.15px | **1.40** |

`ch`는 **숫자 "0"의 폭**입니다. 한글은 그보다 1.4배 넓습니다.
그래서 `max-w-[22ch]`는 한글 22자가 아니라 **15.7자**에서 줄이 바뀝니다.

### 게다가 래퍼에 걸면 한 번 더 좁아진다

`ch`·`em`은 **그 요소 자신의 font-size**로 계산됩니다. 글자 크기가 없는 래퍼에 걸면
루트(16px) 기준이 됩니다.

| 위치 | 코드 | 의도 | **실측** | 실제 줄당 한글 |
| --- | --- | --- | --- | --- |
| C-1 도입 자막 | `max-w-[28ch]` (래퍼) | 553px | **266.9px** | **9.6자** |
| C-3 캐릭터 대사 | `max-w-[30ch]` (래퍼) | 574px | **285.9px** | **8.6자** |
| C-2 장면 자막 | `max-w-[22ch]` (`<p>`) | 434px | 434.5px | 15.7자 |

C-1·C-3은 래퍼에 걸려 **의도의 절반**입니다. C-3 대사가 한 문장에 5줄이 나던 이유입니다.

> 1차 작업에서 C-2 자막의 같은 문제를 고쳤지만 **`ch`가 한글 폭이 아니라는 것까지는
> 보지 못했습니다.** 그래서 `<p>`로 옮기는 것만 하고 숫자는 그대로 뒀습니다.

### 결정 D1 — 전용 유틸리티 클래스를 만든다

화면 명세 §1-3은 **"아이 화면 본문은 줄당 최대 22자"** 입니다. 22자를 만드는 값은
`22 × 0.864em = 19em`입니다. 숫자를 화면마다 흩뿌리지 않고 클래스 하나로 둡니다.

```css
/* globals.css
   아이 화면 본문 줄 길이 상한 — 줄당 한글 22자 (screens.md §1-3)
   ⚠️ ch를 쓰지 않는다. ch는 "0"의 폭(0.617em)이고 한글은 0.864em이라 1.4배 좁다.
   ⚠️ 반드시 **글자 크기를 가진 요소에** 건다. 래퍼에 걸면 루트 16px로 계산된다. */
.kid-line { max-width: 19em; }
```

적용 후 (32px 기준 608px · 31px 기준 589px):

| 위치 | 전 | 후 | 배율 |
| --- | --- | --- | --- |
| C-1 도입 자막 | 266.9px | **608px** | **2.28×** |
| C-3 캐릭터 대사 | 285.9px | **589px** | **2.06×** |
| C-2 장면 자막 | 434.5px | **608px** | 1.40× |
| C-12 마무리 대사 | 368px | **720px** (§8) | 1.96× |

요구 6의 "2배 정도"와 요구 8의 "늘려줘"가 **22자 규칙 하나로 동시에 충족**됩니다.

> 좌측 패널의 물리적 한계는 768 − 80(`px-10`) = **688px**입니다. 608px은 그 안에 들어갑니다.
> C-2 자막만 2배(869px)가 안 되는데, 패널을 넘기 때문입니다. 22자 규칙을 지키는 608px이 상한입니다.

## 1. 홈 — 이어하기와 추천을 같은 행에 🟢

### 요구
태블릿에서도 [이어하기]와 [추천 이야기]가 같은 행에. 그만큼 콘텐츠·폰트가 작아진다.

### 현재
[HomeScreen.tsx:102](../src/features/home/HomeScreen.tsx#L102)

```tsx
<div className="mt-6 flex flex-col gap-6 xl:flex-row">
  <section className="min-w-0 xl:w-[58%]">   {/* 이어하기 */}
  <section className="... xl:w-[42%]">        {/* 추천 */}
```

`xl:` = **1280px**. 태블릿 폭은 1133·1180이므로 미달 → 세로로 쌓입니다.

### 원인
브레이크포인트를 잘못 골랐습니다. 지원 태블릿 최소 폭이 1133px이므로 `lg:`(1024px)여야 합니다.

### 결정 D2 — `lg:`로 내리고 flex를 grid로 바꾼다

`flex` + `w-[58%]`/`w-[42%]`는 **gap 24px을 계산에 넣지 못해** 합이 100%+24px이 됩니다.
지금은 `min-w-0`으로 눌려 티가 안 날 뿐입니다. grid는 gap을 먼저 빼고 나눕니다.

```tsx
<div className="mt-6 grid gap-6 lg:grid-cols-[58fr_42fr]">
```

### 각 폭에서 실제로 얼마가 남는가

사이드바 240px(`w-60`) + 본문 좌우 여백 80px(`px-10`)을 뺀 값입니다.

| 뷰포트 | 본문 폭 | 이어하기(58%) | 추천(42%) |
| --- | --- | --- | --- |
| 1133×744 | 813px | 458px | 331px |
| 1180×820 | 860px | 485px | 351px |
| 1280×800 | 960px | 543px | 393px |
| 1366×1024 | 1046px | 594px | 428px |

### 폰트는 줄이지 않는다 (판단)

요구는 "콘텐츠가 작아지고 폰트도 조정될 것"이었습니다. 실제로는 **요구 2(추천을 목록
형식으로)가 그 축소를 이미 달성**합니다. 큰 카드 2장이 세로로 쌓이던 자리에 88px 썸네일
행 2개가 들어가므로, 폰트를 더 줄이면 아이 화면 하한(§1-3)에 가까워집니다.

1133×744에서 세로가 넘치는지는 검증으로 확인합니다 (계산상 501/566px로 들어갑니다).
넘치면 **표지 비율을 16:9 → 2:1로 낮춰** 높이만 줄입니다. 폰트는 마지막 수단입니다.

## 2. 홈 — 추천을 목록 형식으로 🟢

### 요구
추천 이야기가 이어하기와 똑같이 거대한 카드 하나로 나온다. 시안처럼 목록으로.

### 현재
추천과 목록 페이지가 같은 `StoryCard`를 씁니다 — 4:3 표지가 위에 붙은 세로 카드입니다.
331px 폭에서 표지만 248px 높이를 먹습니다.

### 결정 D3 — `StoryListRow` 컴포넌트를 새로 만든다

`StoryCard`를 고치지 않습니다. 목록 페이지(B-2)·마이페이지(F-1)가 같은 컴포넌트를 쓰고
있어 거기까지 바뀝니다. 홈 추천 전용 가로형 행을 따로 만듭니다.

```
┌──────────────────────────────────────────┐
│ ┌────────┐  호랑이와 하나                 │   높이 96px
│ │ 88×66  │  ⏱ 약 20분                     │   썸네일 4:3
│ │  표지   │  [다름] [자기이해]              │
│ └────────┘                                │
└──────────────────────────────────────────┘
```

- 썸네일 **88×66** (4:3) — 표지 미수령이라 지금은 `primary-soft` 색면
- 제목 `text-parent-body`(16px) bold · 1줄, 넘치면 `truncate`
- 소요 시간 `text-sm` · 주제 칩 `text-sm`, **최대 2개**만 (331px에서 3개는 넘칩니다)
- 전체가 `<Link href="/stories/{id}">` — 기존 경로 그대로 B-3으로 갑니다

### 이어하기가 없을 때는? (검토에서 확인됨)

지금은 3열 그리드로 `StoryCard`를 씁니다. **그대로 둡니다** — 자리가 넉넉할 때
표지를 크게 보여주는 게 아이에게 유리하고, 목록 형식은 좁은 폭의 해법입니다.

> ✅ **2026-08-13 검토** — 요구대로입니다. 목록 형식은 **이어하기가 있을 때 우측 42%에만**
> 씁니다. 이어하기가 없으면 **카드 3열**, 이야기 목록 페이지(B-2)도 **카드 3열**입니다.

### 결정 D3a — 추천은 3개를 기준으로 한다

검토에서 확정됐습니다. 세 화면 모두 **3개**입니다.

| 화면 | 형식 | 개수 |
| --- | --- | --- |
| 홈 · 이어하기 있음 | 목록 행 (우측 42%) | 3 |
| 홈 · 이어하기 없음 | 카드 3열 | 3 |
| 이야기 목록 B-2 | 카드 3열 | 서버가 준 전부 |

**개수를 프론트가 만들지 않습니다.** 서버가 준 배열을 그대로 그립니다(1차 D5).
문제는 **목 카탈로그에 이야기가 1편뿐**이어서 3개인 화면을 볼 수 없다는 것입니다.

**결정** — 목 카탈로그에 **카탈로그 전용 2편**을 추가합니다.

| 항목 | 값 |
| --- | --- |
| 추가 | `호랑이와 하나` · `해님과 달님` |
| 어디까지 | B-1 추천 · B-2 목록 · B-3 상세까지 정상 동작 |
| 재생 | **불가.** B-3의 `이야기 시작하기`가 비활성이고 `준비 중이에요` 안내가 뜬다 |

- 시작 버튼을 살려두면 **막다른 길**입니다. 장면 데이터가 없어 `/play`에서 깨집니다
- "준비 중"은 거짓이 아닙니다 — 실제로 콘텐츠가 아직 없습니다
- 이걸 넣으면 **요구 1·2·3을 다 볼 수 있습니다.** 지금은 이야기가 1편이라
  "태블릿에서 3열"도 눈으로 확인할 수 없습니다
- `availableTopics`는 세 편의 주제를 **합집합**으로 냅니다 (지금은 1편 것만 냅니다)

## 3. 이어하기 없는 상태를 테스트할 방법 🟢

### 요구
이어하기가 없을 때 추천만 나오는 형태를 볼 방법이 없다.

### 현재
목의 `getHome`은 진행 중 세션이 있으면 `inProgress`를 채웁니다
([mock-account.ts:171](../src/lib/api/mock-account.ts#L171)).
비우려면 `/login`의 **데모 상태 초기화**로 계정·아이·세션을 전부 지우고 온보딩을
다시 해야 합니다. 확인 한 번에 로그인부터 다시 하는 셈입니다.

### 결정 D4 — 개발 전용 URL 전환을 붙인다

`?api=` · `?speech=`와 **같은 방식**입니다. 새 장치를 만들지 않습니다.

| 파라미터 | 동작 |
| --- | --- |
| `/home?home=fresh` | `inProgress`를 무시하고 추천만 그린다 |
| `/home?recommend=3` | 추천 목록을 3개로 늘린다 (목록 형식 확인용) |

구현 규칙:

- `process.env.NODE_ENV !== "development"`면 **즉시 반환**. 프로덕션 빌드에서 분기가 접힙니다
- **서버 데이터를 조작하지 않습니다.** 받아온 스냅샷을 그리는 단계에서만 가립니다.
  세션은 살아 있고, 파라미터를 떼면 원래대로 돌아옵니다
- ~~전환이 켜져 있으면 점선 칩을 띄웁니다~~ → **`?home=fresh`에는 칩을 띄우지 않습니다**
  (2026-08-13 지시). 주소에 이미 `home=fresh`가 보이고, 빈 상태 **레이아웃을 확인하려는**
  화면에 안내 칩이 끼면 그 배치를 그대로 볼 수 없습니다.
  `?recommend=`는 칩을 남깁니다 — 그쪽은 **없는 이야기를 늘려 보여주는** 것이라
  실제 데이터로 오인하면 안 됩니다. 성격이 다릅니다
- `?recommend=n`이 만드는 추가 행은 **목 카탈로그에 없는 더미**입니다. 눌러도 상세가
  없으니 "이야기를 찾을 수 없어요"가 뜹니다 — **레이아웃 확인 전용**이라고 칩에 적습니다

## 5. 이야기 상세 — 이름 줄바꿈 · 뒤로가기 여백 🟢

### 요구 5-1 — 캐릭터 이름이 2줄로 바뀐다

[StoryDetailScreen.tsx:270](../src/features/stories/StoryDetailScreen.tsx#L270)

```tsx
<li className="flex w-20 flex-col items-center gap-2 text-center">
```

`w-20` = **80px** 고정입니다. `text-sm`(14px)에서 한글 1자는 12.1px이므로
**6.6자**가 한계입니다.

| 이름 | 글자 수 | 결과 |
| --- | --- | --- |
| 시아버지 | 4 | 1줄 |
| 마을 이장 | 5(+공백) | 1줄 |
| **방귀쟁이 며느리** | **7(+공백)** | **2줄** |

**결정 D6** — 고정 폭을 없애고 이름은 줄바꿈하지 않습니다.

```tsx
<li className="flex min-w-20 flex-col items-center gap-2">
  <CharacterPortrait ... size={72} />
  <span className="whitespace-nowrap text-sm font-bold text-text">{displayName}</span>
</li>
```

부모가 `flex-wrap gap-6`이므로 항목이 길어지면 다음 줄로 넘어갑니다. 초상은
`min-w-20`으로 최소 폭을 지켜 좁은 이름이어도 간격이 흐트러지지 않습니다.

### 요구 5-2 — 뒤로가기가 표지 모서리에 딱 붙어 있다

```tsx
<div className="... p-6 ...">              {/* 여백 24px */}
  <BackButton className="absolute top-6 left-6 z-10" />   {/* 24px — 표지가 시작하는 좌표 */}
  <div className="... rounded-card">표지</div>
```

여백이 24px이고 버튼도 24px에 있어 **표지의 좌상단 모서리 정확히 그 지점**에 얹힙니다.
둥근 모서리와 사각 버튼이 겹쳐 답답해 보입니다.

**결정 D7 (2026-08-13 검토로 개정)** — 겹치기를 유지하고 **표지 안쪽으로 20px 들여놓습니다.**

```
┌──────────────────────────┐
│ ╭──────────────────────╮ │
│ │  [←]                 │ │  ← 표지 위에 얹되 모서리에서 20px 떨어진다
│ │        표지           │ │
│ ╰──────────────────────╯ │
└──────────────────────────┘
```

```tsx
{/* 표지 컨테이너 안으로 넣는다. 바깥 패딩(p-6)에 의존하면
    패딩을 바꿀 때마다 버튼이 모서리로 다시 붙는다. */}
<div className="relative flex size-full ... rounded-card">
  <BackButton className="absolute top-5 left-5 z-10" />
```

- 오프셋 기준을 **바깥 패딩이 아니라 표지 자신**으로 바꿉니다. 지금은 `p-6`(24px)과
  `top-6`(24px)이 같아서 버튼이 표지가 시작하는 좌표 **정확히 그 지점**에 앉습니다
- 20px이면 `rounded-card`(28px) 곡선 안에 완전히 들어갑니다.

## 7. NPC 발화 점등 · "이제 말해 볼까?" 위치 🟢

### 요구 7-1 — NPC가 말할 때 초상 테두리가 점등되면 좋겠다

**현재도 표시는 있습니다.** [CharacterPortrait.tsx:34](../src/features/play/CharacterPortrait.tsx#L34)

```tsx
{speaking ? <span className="absolute animate-ping rounded-full bg-info/35" /> : null}
...
speaking ? "ring-4 ring-info" : ""
```

- `ring-4 ring-info` — **고정** 파란 링 (움직이지 않습니다)
- `animate-ping` — 뒤에서 1.22배로 퍼지며 사라지는 후광. 160px 초상에서 `bg-info/35`는
  거의 안 보입니다

즉 "말하고 있다"를 알리는 건 사실상 **정지된 링**이고, 요구는 **테두리 자체가 점등**입니다.

**결정 D10** — 링을 맥동시킵니다. `ping` 후광은 뺍니다.

```css
/* globals.css */
@keyframes speaking-ring {
  0%, 100% { box-shadow: 0 0 0 3px var(--color-info), 0 0 0 6px transparent; }
  50%      { box-shadow: 0 0 0 5px var(--color-info), 0 0 0 14px color-mix(in oklab, var(--color-info) 22%, transparent); }
}
.animate-speaking-ring { animation: speaking-ring 1.1s ease-in-out infinite; }
```

- 두께(3→5px)와 번짐(0→14px)이 함께 커져 **테두리가 숨 쉬는** 것으로 읽힙니다
- 주기 1.1s — 말하는 속도와 비슷해 "말할 때마다"로 느껴집니다.
  실제 음량에 맞추지 않습니다(원본 음성을 다루지 않습니다 · PRD 10.3)
- `prefers-reduced-motion`에서는 애니메이션을 끄고 **`ring-4 ring-info` 정적 링을 남깁니다.**
  움직임만 빼고 정보는 유지합니다
- `ping` 제거로 `absolute` 후광 요소가 없어져 레이아웃이 단순해집니다

### 요구 7-2 — "이제 말해 볼까?"가 너무 위에 붙어 있다

**붙어 있는 정도가 아니라 잘립니다.** 1280×800 스크린샷에서 이 문구는 우측 패널 상단
경계에 걸려 위쪽이 잘리고, 셸의 **잠시 멈춤** 버튼과도 겹칩니다.

원인: [panels.tsx:153](../src/features/play/panels.tsx#L153)

```tsx
<div className="flex min-h-0 flex-1 flex-col items-center justify-center gap-3 overflow-hidden px-6">
  <p className="shrink-0 ... text-turn ...">이제 말해 볼까?</p>
  <div className="flex min-h-0 w-full flex-1 ...">  {/* 마이크가 flex-1 */}
```

마이크 칸이 `flex-1`로 **남은 높이를 전부** 가져가므로 열이 꽉 찹니다. 그러면 부모의
`justify-center`가 할 일이 없어져 문구가 y=0에 앉고, `text-turn`(32px)의 위쪽이 잘립니다.

**결정 D11** — 상단 여백을 주고, 잠시 멈춤 버튼을 피합니다.

```tsx
<div className="... px-6 pt-6 pr-28">
```

`pt-6`(24px)로 잘림을 없애고, `pr-28`(112px)로 잠시 멈춤 버튼 아래를 비웁니다.
1차에서 `ConversationPanel`에 같은 `pr-28`을 넣은 것과 같은 처리입니다.

### 요구 9-1 — 순차 진행 (1 → 2 → 3 → 4) 🟡 **백엔드 신호 필요**

현재 완료 판정은 이렇습니다 ([MissionCard.tsx:84](../src/features/play/MissionCard.tsx#L84)):

```tsx
const done = accumulatedElements.includes(item.element);
```

**여기서 막힙니다.** 1번과 2번이 둘 다 `SOLUTION`입니다. 서버가 `SOLUTION`을 확정하는
순간 **1번과 2번이 동시에 완료**됩니다. `accumulatedElements`는 누적 **집합**이라
"SOLUTION을 두 번 채웠다"를 표현할 수 없습니다. 미션 2도 `PERSPECTIVE`가 2개로 같습니다.

즉 요구대로 "1번을 확인하고 넘어가면 2번"을 하려면 **항목 단위 신호**가 필요합니다.

**백엔드 요청 (별도 문서로 제출)**

`POST /api/sessions/{id}/messages` 응답에 추가:

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `missionProgress.satisfiedIndexes` | integer[] | 선택 | 충족된 체크리스트 **인덱스** 목록 |

**결정 D14 — 신호가 오기 전까지의 임시 동작**

> 미션 중 아이 발화 **1회 = 항목 1개 진행**. 포인터 앞의 항목은 완료로 표시합니다.

- 이것은 **채점이 아닙니다.** 완료 표시의 뜻은 "맞았어요"가 아니라 **"말했어요"** 입니다
  (지금도 스크린리더 문구가 `말했어요`입니다). 아이가 그 항목에 대해 말한 것은 사실입니다
- 서버가 `accumulatedElements`로 확정한 요소가 뒤쪽 항목까지 덮으면 그 항목도 완료로
  올립니다. **완료를 되돌리지 않습니다**(단조 증가) — 채웠던 별이 사라지면 아이가 혼란스럽습니다
- `missionProgress`가 응답에 실려 오면 그때부터 **그 값을 우선**합니다. 화면 코드는
  포인터를 어디서 얻는지만 바뀌고 렌더링은 그대로입니다

### 요구 9-1b — 브리프 카드의 배치 (2026-08-13 검토에서 추가) 🟢

검토에서 나온 요구 3건입니다.

> 잠시 멈춤이 굳이 미션 카드 안에 있어야 할지 의문이고, 각 항목을 한 줄에 하나씩 보여주면
> 더 좋을 것 같고, [말해볼래요]도 카드 안에 있을 필요가 없고, 카드를 우측 패널 세로 중앙에.

**결정 D21 — 체크리스트를 1열 4행으로**

1차 계획은 2×2였고, 그 근거는 "세로 1열은 4개 중 2개만 보인다"였습니다.
**그 근거가 사라졌습니다** — 브리프 상태에서는 마이크를 그리지 않으므로(D16) 우측 패널
전체가 카드 차지입니다.

한 줄에 하나면 **읽는 순서가 곧 말하는 순서**가 됩니다. 2×2는 Z자로 읽어야 해서
"1 → 2 → 3 → 4"라는 순차 진행과 어긋납니다.

폭 검산 — 가장 긴 항목 `며느리에게 어떻게 부탁할까?` 13자 × 18.15px = 236px,
번호 원 24 + 간격 8 + 안쪽 여백 24 = **292px**. 우측 패널은 1133px에서 453px,
1280px에서 512px이므로 **한 줄에 들어갑니다.**

**결정 D22 — 카드를 세로 중앙에 놓고 `pr-28`을 없앤다**

```
┌─ 우측 패널 ───────────────────[잠시 멈춤]─┐
│                                            │  ← 비어 있다. 잠시 멈춤이 숨 쉰다
│    ┌──────────────────────────────────┐   │
│    │ [미션]  높은 배를 어떻게 딸까?      │   │
│    │  ✓  무엇을 사용할까?               │   │  ← 세로 중앙
│    │  ②  사람들은 어디로 피할까?         │   │
│    │  ③  며느리에게 어떻게 부탁할까?     │   │
│    │  ④  그러면 어떤 일이 생길까?        │   │
│    │  지금 말해볼 것                     │   │
│    │  [ 방법 ]                          │   │
│    └──────────────────────────────────┘   │
│                                            │
│            [  말해볼래요  ]                │  ← 카드 밖 · 하단
└────────────────────────────────────────────┘
```

`pr-28`(112px)은 **잠시 멈춤 버튼을 피하려고** 넣은 것이었습니다. 카드를 세로 중앙에
두면 카드 위쪽에 빈 공간이 생겨 **겹칠 일이 없어집니다.** 회피용 여백이 필요 없어집니다.

높이 검산 (1133×744, 우측 패널 744px):

| 요소 | 높이 |
| --- | --- |
| 카드 안쪽 여백 (위+아래) | 32px |
| `[미션]` 칩 + 제목 | 70px |
| 항목 4개 (47px × 4 + 간격 8 × 3) | 212px |
| `지금 말해볼 것` + 칩 | 62px |
| **카드 합계** | **376px** |
| 하단 버튼 영역 | 92px |

376px을 (744 − 92)의 중앙에 두면 카드 상단이 **y=138px**입니다.
잠시 멈춤 버튼은 y=76px에서 끝나므로 **62px 여유**가 남습니다.
미션 2의 힌트가 붙어도(+50px) y=113px로 여전히 겹치지 않습니다.

`max-h-[62%]`도 없앱니다 — 내용 높이대로 놓고, 넘칠 때만 카드가 스크롤합니다.

**결정 D23 — `말해볼래요`를 카드 밖 하단 중앙으로, 채움 버튼으로**

- 카드 밖으로 나오면 **"카드는 읽을 것, 버튼은 할 것"** 으로 역할이 갈립니다
- `보내기`와 같은 하단 자리라 손 위치가 일관됩니다 (태블릿에서 중요합니다)
- **`outlined` → 채움 `primary`.** 이 화면의 유일한 행동이고, 누르면 내 차례가 시작됩니다.
  §1-5가 `primary`를 "주요 CTA · 내 차례"로 정했으니 색이 뜻과 맞습니다
- `보내기`처럼 우측 정렬하지 않고 **중앙**입니다. 카드가 중앙이라 축을 맞춥니다

### 요구 9-3 — 미션은 읽고 나서 [말해볼래요]로 발화 시작 🟢

```
  → 캐릭터 TTS 재생 (좌측: 장면 이미지)
  → TTS 끝 ─ brief가 열려 있으면 CHILD_TURN으로 가지 않는다
  → 아이가 [말해볼래요] ─ missionBriefOpen = false, CHILD_TURN 시작
  → 아이 발화 · 제출 → 서버 응답
  → 남은 항목이 있으면 missionBriefOpen = true (다음 항목으로)
  → 4개를 다 채우면 열지 않는다 (일반 대화로 복귀)
```

- `MISSION_DISMISS`는 `mission: null`을 **더 이상 하지 않습니다.** 카드가 4번 돌아와야 합니다
- 브리프가 열린 동안 우측은 카드만, **마이크는 그리지 않습니다.**
  마이크가 보이면 "지금 말해도 되나?"를 아이가 판단해야 합니다

### 요구 9-4 — 발화 중에는 미션 카드를 감춘다 🟢

**결정 D17** — `CHILD_TURN`·`TRANSCRIBING`에서는 카드를 렌더하지 않고 기존
`ChildTurnPanel`을 전체 높이로 씁니다. 미션 때문에 좁아지던 마이크가 원래 크기로 돌아옵니다.

**단, 현재 항목은 한 줄로 남깁니다.**

```
┌────────────────────────────┐
│ [미션] 무엇을 사용할까?      │  ← 24px 한 줄. 카드가 아니다
│                            │
│      이제 말해 볼까?         │
│          ◯ 마이크           │
└────────────────────────────┘
```

카드를 없애면 아이가 방금 읽은 항목을 잊습니다. 카드는 감추되 **무엇을 말할지는 남깁니다.**
요구는 "카드를 보여주지 않아도 된다"였고, 이 한 줄은 카드가 아닙니다.

### 요구 9-5 — 현재 항목 하이라이트 · 완료 표시 🟢

**결정 D18** — 색과 굵기로만 구분합니다. `[완료]` 텍스트는 쓰지 않습니다.

| 상태 | 배경 | 번호 원 | 글자 |
| --- | --- | --- | --- |
| 완료 | `bg-secondary-soft` | `bg-secondary` 흰 ✓ | `text-muted` (한 톤 낮춤) |
| **현재** | `bg-surface` + **`ring-2 ring-primary`** | `bg-primary` 흰 숫자 | `text-text` **bold** |
| 대기 | `bg-surface/60` | `bg-primary-soft` 회색 숫자 | `text-muted` |

- 현재 항목만 링과 bold를 가집니다. 시선이 한 곳으로 갑니다
- 완료는 초록 계열(`secondary`), 현재는 주색(`primary`) — §1-5의 색 규칙과 맞습니다
- 대기 항목도 **읽을 수는 있습니다.** 가리면 미션이 4단계라는 걸 알 수 없습니다
- 스크린리더 문구는 유지: `말했어요` / `지금 말할 차례예요` / `아직이에요`

### 좌측 패널은?

`showScene = SCENE_NARRATION || mission !== null`이 현재 조건입니다. 미션이 살아 있는
동안 계속 참이 되어 **아이 발화 중에도 캐릭터 얼굴이 안 보입니다.**

**결정 D19** — `showScene = SCENE_NARRATION || missionBriefOpen`.
브리프를 읽을 때는 장면 이미지, 말할 때는 캐릭터 무대(흐림)로 돌아옵니다.

## 10. 카드 순서 — 틀린 항목만 빨간 테두리 🟡 **백엔드 신호 필요**

### 요구
틀린 항목만 빨간 테두리, 맞은 항목은 현재 테두리 유지.

### 왜 지금은 불가능한가

[CardOrdering.tsx:29](../src/features/activity/CardOrdering.tsx#L29)에 이미 적어둔 그대로입니다.

> ⚠️ 서버는 **어느 카드가 틀렸는지 알려주지 않는다**(`hintCardId` 없음).

`POST /activity/order` 응답은 `isCorrect`(전체 정오)와, 3회째에만 `correctOrder`입니다.
프론트는 **정답 순서를 모릅니다**(§0-2 · PRD 8.11). 1·2회째에 특정 칸을 빨갛게 하려면
정답을 알아야 하고, 그러려면 프론트가 채점해야 합니다. 그건 규칙 위반입니다.

그래서 1차에서는 **배치 전체**에 빨간 테두리를 넣었습니다(계획 D6 이탈 기록).

### 백엔드 요청 (별도 문서로 제출)

`POST /api/sessions/{id}/activity/order` 응답에 추가:

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `slotResults` | boolean[] | 선택 | 제출한 순서대로 각 칸이 **정답 위치인지** |

`[true, false, false, true]`처럼 옵니다. 정답 순서 자체는 여전히 내려주지 않으므로
프론트가 정답을 역산하지 못합니다 — 원칙을 깨지 않고 요구를 만족하는 최소 필드입니다.

### 결정 D20 — 필드가 있으면 칸 단위, 없으면 지금처럼

```tsx
const wrong = slotResults ? slotResults[i] === false : mismatched;
```

- `slotResults`가 오면 **틀린 칸만** `border-danger`, 맞은 칸은 현재 테두리 유지
- 안 오면 지금 동작(배치 전체) 그대로. **백엔드를 기다리며 화면이 멈추지 않습니다**
- 3회째에는 어느 쪽이든 빨간 테두리를 붙이지 않습니다 (다음 시도가 없는데 지적만 남습니다)
- 맞은 칸에 초록 테두리를 **넣지 않습니다.** 요구는 "현재 테두리 유지"였고,
  초록을 넣으면 정답 개수를 세는 화면이 됩니다 (점수 금지 · PRD 10.3)

## 16. 구현 완료 기록 (2026-08-13)

10단계 전부 끝났습니다. **계획과 달라진 것과 구현 중에 찾은 결함**만 적습니다.

### 🔴 가장 큰 발견 — 아이가 영구히 멈추는 버그

미션이 4항목을 다 끝내기 전에 **장면의 턴 한도가 먼저 차서 장면이 닫히면**,
`missionBriefOpen`이 true로 남습니다. 다음 장면에서 `applySnapshot`이 `mission`만
null로 지우고 이 플래그는 그대로 두는데, `CHARACTER_TTS_DONE`이 그 플래그를 보고
**아이 차례로 넘기지 않습니다.**

우측 패널은 `mission`이 null이라 브리프 대신 평소 대화 패널을 그립니다.
**화면은 완전히 정상으로 보이고, 말할 차례만 영원히 오지 않습니다.**

| | |
| --- | --- |
| 찾은 방법 | `handoff` 스위트가 장면 4에서 완주 실패. 처음엔 반복 부족으로 **오진**했다 |
| 고친 것 | `applySnapshot`이 미션 상태 **세 값을 함께** 지운다 (`mission`·`missionBriefOpen`·`missionTurns`) |
| 안전장치 | `CHARACTER_TTS_DONE`의 차단 조건에 `mission !== null` 추가 — 이 전환을 막는 건 **누를 버튼이 화면에 있을 때만** 안전하다 |
| 결과 | 같은 시나리오가 180초 타임아웃 → **33초 완주** |

> 이 버그는 **미션 개편이 만든 것**입니다. 예전에는 `MISSION_DISMISS`가 미션을
> 영구 제거해 브리프가 두 번 뜰 일이 없었고, 그래서 "장면이 미션보다 먼저 닫히는"
> 경우가 존재하지 않았습니다.

### 그 외 구현 중에 찾은 결함 3건

## 17. 추가 요구 — C-3 우측 패널에 그 캐릭터와의 대화 전체 (2026-08-13)

### 요구

> 우측 패널에 NPC의 대사가 나오는 타이밍이 있는데, 이때 NPC와 아이와의 대화 내역을
> 전부 보여주는 건 어때? 해당 NPC와 아이와의 대화 내역 전체를 보여주는 거지.

### 왜 의미가 있나 — 같은 캐릭터가 여러 장면에 나온다

| 장면 | 캐릭터 |
| --- | --- |
| 3 | **방귀쟁이 며느리** |
| 5 | 시아버지 |
| 7 | 마을 이장 |
| 9 | **방귀쟁이 며느리** ← 재등장 |

그래서 "그 NPC와의 대화 전체"는 "현재 장면의 대화"와 **실제로 다릅니다.**
장면 9에서 장면 3의 대화를 함께 보여줄 수 있습니다.

### 결정 D24 — NPC 단위로 모으고, 지난 장면에는 구분선을 넣는다

```
방귀쟁이 며느리와 나눈 이야기   [말하는 중]
───────── 지난 이야기 ─────────
  민준아, 내 방귀가 너무 크다는 걸…      ← 장면 3
              며느리가 창피해서…
  그렇게 말해 주니 창피한 마음이…
───────── 지금 이야기 ─────────
  민준이 덕분에 내 방귀가…              ← 장면 9
```

- **다른 캐릭터 대사는 섞지 않습니다.** 세션 전체를 그대로 부으면 누가 말했는지
  알 수 없습니다 — 원래 장면 단위로 자른 이유가 그것이었습니다
- 구분선이 필요한 이유: 장면 3의 대화와 장면 9의 대화는 **서로 다른 순간**입니다.
  이어 붙이면 한 번에 이어진 대화로 읽혀 아이가 헷갈립니다
- 자동 스크롤이 이미 있어 최신 대사가 항상 보입니다

### 데이터 한계 🟡 — 메시지에 캐릭터 정보가 없다

서버가 주는 `messages[]`에는 `sceneId`만 있고 **캐릭터가 없습니다.** 캐릭터는
`currentScene`에만 실려 오므로, 지난 장면 대사가 누구 것인지 응답만으로는 모릅니다.

**임시 동작** — 장면이 로드될 때마다 `sceneId → 캐릭터` 짝을 프론트가 기억합니다
(`sceneCharacterRef`). 처음부터 이어서 진행하는 동안에는 완전합니다.

⚠️ **이어하기로 중간 진입하면** 지난 장면의 짝을 모릅니다. 그때는 짝을 모르는 장면을
**빼고** 보여줍니다 — 다른 캐릭터 대사를 섞는 것보다 덜 보여주는 쪽이 안전합니다.
[요청 문서](../../docs/request/backend/message-character.md)로 필드를 요청해 뒀습니다.

### 함께 고친 것 2건

| 항목 | 무엇이었나 |
| --- | --- |
| 대화 내역 맨 위가 **잠시 멈춤 버튼에 가림** | 헤더가 48px인데 버튼은 y=24~68이라 20px이 스크롤 영역으로 넘어왔다. 헤더에 `min-h-[4.5rem]`(72px)을 줘서 버튼이 헤더 안에서 끝나게 했다 |
| **"며느리이(가) 말하고 있어요"** | 조사를 `이(가)`로 두면 사람이 쓰지 않는 문장이 된다. `korean.ts`에 이미 있던 `hasFinalConsonant`로 `subjectParticle()`을 만들어 **며느리가 / 이장이**로 고른다. 캐릭터 이름은 이야기마다 바뀌므로 문구를 손으로 정할 수 없다 |

### 검증

`handoff` 스위트가 완주하면서 C-3마다 우측 패널을 기록합니다.

```
방귀쟁이 며느리 — 말풍선 1개
시아버지 — 말풍선 1개
마을 이장 — 말풍선 1개
방귀쟁이 며느리 — 말풍선 10개 · 지난 이야기 구분선
OK   같은 캐릭터가 여러 장면에 재등장 — 방귀쟁이 며느리
OK   재등장 장면에 "지난 이야기" 구분선
OK   재등장 장면이 지난 대화까지 보여준다 — 첫 등장 1개 → 재등장 10개
OK   한 패널에 한 캐릭터만
```

> 이 검사를 넣으려고 `handoff`의 TTS 스텁 지연을 25ms → **600ms**로 올렸습니다.
> 25ms면 C-3(캐릭터 발화 중)이 눈 깜빡할 사이에 지나가 350ms마다 살펴보는 루프가
> **그 상태를 거의 못 잡습니다.** 실제 TTS는 몇 초씩 걸리니 600ms도 여전히 빠른 쪽입니다.

## 18. 추가 요구 — 미션 2는 택 1 방식 (2026-08-13)

### 요구

> 미션 2는 미션 1과 달라. 미션2는 4개 중 하나를 선택해서 진행하는 거야. 4가지 항목 중
> 하나를 선택해서 선택한 항목에 따라 아래 예시 문장이 바뀌어.
> 그리고 미션2의 경우에 아이가 말해볼래요를 눌러서 말을 했는데 실패할 경우 힌트를 줄 예정이야.

### 확인 — 명세에 이미 다 있었다

| 문서 | 내용 |
| --- | --- |
| [화면 명세 C-11](../../docs/spec/screens.md) | 친구 카드 4장 · 선택 시 primary 테두리 + 체크 뱃지 · 문장 틀 `"{선택한 친구}는 ______ 할 수 있어요."`(빈칸은 점선) |
| [PRD 7.6](../../docs/product/prd.md) | 친구 4종과 **예시 문장 4개**. "처음부터 미션을 보여주면 아이가 정해진 답을 찾으려 한다" |
| [api-spec 6.1](../../backend/docs/api-spec.md) | `missionTriggered.checklist[]` — **`mission_2`는 항상 빈 배열** |

**즉 서버는 미션 2의 선택지를 주지 않습니다.** 미션 정의를 별도 테이블에 두지 않고
**코드 상수로 관리한다**는 팀 결정 때문입니다(PRD 7.6 "미션 데이터 처리 방침").
그래서 4종은 프론트 상수(`features/play/mission2.ts`)에 둡니다 — 지어낸 값이 아니라
명세·PRD에 적힌 값을 옮긴 것입니다.

### 결정 D25 — 컴포넌트를 나눈다

`MissionCard`(순차)와 `Mission2Card`(택 1)를 따로 둡니다. 한 파일에서 분기하면
**순차 포인터와 선택 상태가 서로를 망칩니다** — 함께 있을 수 없는 개념입니다.

미션 종류 판별은 **서버가 주는 `id`** 로 합니다. `mission_1`·`mission_2`는 UUID가 아니라
계약에 박힌 고정 문자열입니다. 제목으로 판단하면 문구가 바뀔 때마다 깨집니다.

```
[미션 2]
친구의 다른 점을 좋은 점으로 바꿔볼까?
단점처럼 보이지만 좋은 일에 쓸 수 있는 점을 찾아보자.

[목소리가 큰]  [질문이 많은]  [힘이 센]  [조용한 ✓]     ← 가로 4열 · 택 1

  조용한 친구는  ⋯⋯⋯⋯⋯  할 수 있어요.               ← 고른 친구로 주어가 바뀐다

  힌트  이렇게 말해도 좋아. "조용한 친구는 다른 사람의 말을 잘 들어 줄 수 있어요."
                                                     ← 재시도에만
        [ 말해볼래요 ]                                ← 고르기 전에는 비활성
```

세부 결정:

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 카드 배열 | **가로 4열 1행** | 2×2로 두면 카드가 두 배로 높아져 **문장 틀과 힌트가 잘린다.** 그림이 작아지는 대신 스크롤이 없다 — 아이 화면에서 스크롤은 마지막 수단이다. 명세 C-11도 가로 배열이다 |
| 고르기 전 | `말해볼래요` **비활성** + "친구를 고르면 말할 수 있어" | 문장 틀의 주어가 빈 상태로 말하게 하면 무엇을 말할지 알 수 없다 |
| 조사 | `topicParticle()`로 `은`/`는` | 지금 네 라벨은 모두 "친구"로 끝나 받침이 없지만, 라벨이 바뀌어도 문장이 깨지지 않아야 한다 |
| 힌트 시점 | **재시도에만** | 처음부터 보여주면 아이가 정해진 답을 찾으려 한다 (PRD 7.6) |
| 힌트 문구 | PRD 7.6 예시 문장을 그대로 인용 | 문장을 새로 만들지 않는다 |
| 재시도 한도 | **2회** (`MISSION2_MAX_ATTEMPTS`) | 무한 재시도는 아이를 미션에 갇히게 한다. 카드 순서 3회 제한(D-10)과 같은 이유 |
